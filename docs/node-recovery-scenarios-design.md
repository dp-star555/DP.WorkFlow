# 流程异常恢复机制：运行场景与结构设计草案

状态：**完整目标仍为设计草案；已有受限V1实现，范围以[异常恢复V1](nodes/fault-recovery-v1.md)为准**。V1开放原操作继续、无环串行命名入口重执行与受监管处理子流程，不开放并行回退、外部故障Case接口和跨进程恢复。处理子流程自身异常时V1保守终止，不盲目从头重放。基线见[恢复代码评审](node-fault-recovery-review.md)，平台待办见[Node平台清单](node-platform-review-backlog.md)。

## 1. 设计目标

任何可被运行时可靠捕获的节点故障，以及宿主/设备监控触发的外部故障，都进入统一的、可操作的故障处置机制。目标不是仅显示错误，也不是把所有异常自动转成重试，而是：停止不应继续的执行、保留现场、允许人员执行处置、验证后恢复原流程。

代码错误也可进入处理会话，但不代表必然允许继续。进程崩溃、严重资源耗尽等超出本进程控制能力的问题，应由外部监督与安全机制处理。

## 2. 五条基础区分

1. **故障来源≠影响范围**：一个节点报错可能影响整个工位；外部门禁故障未必属于任何单个节点。
2. **严重度≠停止方式**：报警等级不能代替对在途操作如何处置的明确要求。
3. **停止调度≠在途调用退出≠设备安全静止**：三种状态必须分别呈现和验证。
4. **故障条件消失≠操作员确认≠流程已具备恢复条件**：三者不能互相代替。
5. **同一NodeId≠同一次操作**：循环、并行、子流程和恢复尝试必须保留完整身份。

## 3. 故障、操作与运行控制分层

### 3.1 统一故障入口

入口包括：准备失败、输入解析失败、Handler显式失败、Handler抛异常、结果提交失败、恢复动作失败、外部故障。

对内部错误保持阶段归属：创建操作之前失败不能假定已有可继续的操作；提交阶段失败不能未经核实重新执行已产生副作用的Handler。主动取消单独保留取消原因，不作为默认节点故障。

### 3.2 统一故障处理会话

会话保存：来源、受影响执行身份/资源、原始故障、附带故障、当前处置状态、允许动作、处理记录及版本。多个相关故障可以有一个处置组，但各故障事实不合并丢失。

动作来源：框架兜底、节点领域扩展、流程配置的恢复子流程。选项有真实执行入口，不是只有文字的按钮。节点未创建操作、或者构建选项失败时，仍提供可信的停止/诊断/上报兜底，不能递归制造新弹框。

### 3.3 统一运行控制与恢复执行

所有内部/外部故障通过同一控制入口收敛调度权限、动作提交和状态转换。节点负责领域核实和处置，不能自行修改其他Token的程序位置。

控制请求有确定的接受顺序；重要的停止/阻断请求不得淹没在无界普通事件队列中。重复外部状态应去重/合并，不生成无限会话。

### 3.4 节点操作扩展

普通节点可使用一次执行适配；可恢复操作按每次逻辑执行保存实例/意图与进度。恢复同一次操作不重新创建意图。节点可扩展查询/修复动作，不要求框架知道轴、机器人或数据库细节。

创建意图应在外部副作用之前；实例不能放在共享Handler字段或NodeModel。具体接口待前述契约确定后再收敛，不要求一次引入大量接口。

## 4. 停止范围与停止方式

### 4.1 影响范围

- 当前操作/顺序路径。
- 当前循环迭代。
- 所属并行作用域。
- 当前Block子运行。
- 整次根运行。
- 宿主/设备级持续阻断条件，影响当前以及后续相关运行。

节点或监控可报告建议范围/设备标识，实际范围由宿主策略确认并允许扩大。范围内资源/共享数据依赖未被证明隔离时，不能默认只停故障节点。当前资源协调尚未完备，第一版应采取保守扩大策略。

### 4.2 三种停止要求

| 要求 | 调度 | 在途操作 | 恢复 |
|---|---|---|---|
| 节点边界暂停 | 阻止新普通操作开始 | 允许已开始操作完成并提交；结束后停驻 | 条件满足后可继续 |
| 受控中断并处置 | 立即阻止新调度 | 请求受影响操作中断/设备受控停止，等待确认；不能保证任意代码立即退出 | 保留操作，核实现场后恢复 |
| 终止本次运行 | 永久关闭本次普通调度 | 请求取消/必要停止，并等待可确认退出 | 不再在该Run上Resume，必要时建立新运行 |

软件停止不是安全急停。门禁、急停等安全需求必须由安全硬件/控制系统独立满足；流程运行时接收状态并阻断调度、执行可控的软件停止和核实，不能成为唯一安全保护。

### 4.3 无法停止的调用

如果SDK调用或用户代码不合作，显示“停止未确认/设备状态未知”，保持恢复阻断，不谎称已暂停安全。超时不能成为强制释放仍在使用资源的理由；需要驱动级停止、进程隔离或现场核实。故障中断只取消本次尝试的执行令牌，不直接耗尽根运行令牌；操作员明确终止时才取消整次运行。

## 5. 执行身份与数据有效性

需要表达以下层次，而不是只追加一个NodeId：

- 根运行身份与子运行/文档调用路径。
- 循环帧路径：循环实例、当前迭代，必要时关联产品/工件身份。
- 并行作用域实例、分支身份与本轮恢复代次。
- 节点逻辑操作OperationId。
- 尝试AttemptId。
- 故障会话CaseId和会话Revision。

现有WorkflowExecutionIdentity已有Run/Token/Scope/节点执行次数，但LoopIteration仅用于循环节点，不能直接代替循环体节点的完整迭代路径。

OperationId不是业务去重键的万能替代：重启一轮、回到检查点或启动新Run后，如果仍在处理同一产品同一业务步骤，数据写入等副作用可能必须继续使用原业务EffectKey。由领域明确保留/重新生成条件，不能因创建新OperationId就重复写入。

### 结果处理

- 保留已经发生的事实，不把暂停解释为回滚。
- 所有输出关联具体操作/尝试/作用域代次；重新执行后的消费者不默认读取被替代尝试的latest值。
- 只在允许的提交点公布标准结果；边界暂停允许已开始操作正常完成。
- 中断请求与成功结果并发时，由控制顺序确定：接受阻断之后不推进后继；迟到成功证据可保存为待核实事实，不能简单丢弃后再次产生副作用。
- 外部请求接受之前已经提交的结果仍是历史事实，不假装撤销。
- 循环/分支/检查点重建时，明确哪些输出仍有效、哪些失效；外部写入不能靠删除内部输出回滚。
- 当前数据提交与输出登记分步实现，提交阶段故障必须先核实实际提交状态，不能直接重跑Handler。

## 6. 场景推演

| 场景 | 阻断与处置 | 合法的继续方式 |
|---|---|---|
| 串行计算节点异常 | 停驻当前路径，保存输入和异常；不会推进后继 | 可重复计算时重试同次输入；代码/配置需修改时停止并重编译，默认不热改运行计划 |
| 绝对定位超时 | 核实运动状态、坐标参考、互锁和原目标 | 已完成则按证据完成；未完成且安全则继续原目标 |
| 相对定位/取料状态未知 | 保存本次意图与进度，禁止盲目重发 | 节点检查原操作，完成/继续/人工处理；无法核实则保持阻断 |
| 外部写入响应丢失 | 查询业务EffectKey，保留“可能已提交”状态 | 确认已写或幂等补写；不伪造exactly-once承诺 |
| 普通循环第7轮检测失败 | 保留第7轮循环帧与操作，不能推进到第8轮 | 修复后继续第7轮；不会因重试节点而重新进料 |
| 需要重做本轮 | 明确撤销本轮控制进度、失效相应数据；确认物料/设备已满足重做前提 | 建立新的本轮执行代次，但按领域保留必要的业务去重身份 |
| 本轮工件应报废 | 执行显式排废/清场业务路径并确认 | 以明确的本轮业务结果结束，再进入下一轮；不是忽略故障并伪造节点成功 |
| 无限循环/回边图 | 错误计数不能每回边自动清零；按故障签名/业务操作预算防止无界恢复 | 第一版只允许明确结构化循环恢复；不能用任意Jump猜测“这一轮”的范围 |
| 并行A失败、B已完成 | 暂停所属并行作用域，关闭Join放行，保存B的完成结果 | 若独立性及数据有效性成立，仅恢复A；Join仍只认可本代每分支的一次有效到达 |
| 并行A失败、B正在运动 | 请求B按声明到边界或受控中断，确认其现场状态 | B已完成则不重发；B被打断则单独核实并继续；A恢复不能自动让B重复动作 |
| 并行B等待A的信号 | 不能要求B无限等到正常完成才处理A；需可取消并保存等待状态 | 中断等待本次尝试，保存分支位置，再按依赖条件恢复；无支持时升级停止 |
| 并行分支共享设备 | 不按图形分支外观认定独立；扩大阻断到设备使用者 | 在资源协调完成前禁止局部自动恢复 |
| 并行多个分支同时失败 | 一个受影响作用域处置组，保留各原始故障和同伴中断原因 | 按允许顺序逐项处理；只处理A不能解除B的阻断 |
| 需要重做整个并行组 | 确认已完成分支的副作用可保留/补偿/去重，替换旧到达记录 | 新Scope代次；不得把旧B到达与新A到达混合成一次成功Join |
| Block内部失败 | 子流程保留准确故障路径，父Block等待；不能再次启动整个Block | 优先子作用域处置；无法处理时上报父作用域，同一故障只有一个处置所有者 |
| 循环里有并行/并行里有Block | 使用完整执行路径，选择包含受影响操作的合法结构化作用域 | 按内到外验证/升级；不能仅按相同NodeId恢复另一次执行 |
| 门禁/气压/PLC监控触发 | 外部事件形成持续阻断条件与故障会话；按实际设备策略请求停止 | 条件恢复、操作员确认、操作状态/资源验证完成后才续跑 |
| 手动Pause时又发生外部故障 | 两种阻断分别保留 | 故障解除不能清掉人工Pause；Resume也不能清掉外部故障 |
| 等待处置期间操作员Stop | 取消处置动作和普通执行，等退出；终止本Run | 晚到的继续按钮/网络响应拒绝，不重新启动 |
| 告警处理步骤自身失败 | 记录为当前会话的处理失败，展示尝试结果，不无限递归打开新处理流程 | 保持原阻断，重新核实/换动作/上报/停止 |
| 准备阶段故障或外部阻断 | 禁止首节点启动；已取得的资源按准备契约清理 | 重新准备需明确准备步骤幂等性，不直接跳过准备进入首节点 |
| 运行结束后收到旧故障事件 | 带旧RunId的请求拒绝作用于新Run | 持续设备条件通过宿主级门禁管理，不能靠旧节点事件猜测当前执行对象 |

## 6A. 处置后回原处继续，还是回到前序步骤

这是恢复的核心执行选择，不只是故障界面的导航。

### 两种“位置”必须分开

- 流程位置：哪一个节点、哪一次操作、哪个阶段、哪一轮/分支。
- 现场位置/状态：轴位置、机器人姿态、夹持物料、产品所在工位等。

回到原节点不自动使设备回到原物理位置；恢复物理位置必须由显式领域动作检查互锁、路径和工件状态后执行。不能通用地把设备移动到异常前快照位置。

### 统一的恢复去向

| 去向 | 语义 | 操作/控制身份 |
|---|---|---|
| 继续原操作 | 节点根据既有意图与进度继续，或检查其是否已完成 | 保留OperationId与当前迭代/分支，尝试递增 |
| 重新尝试原操作 | 用明确的原输入策略重做安全可重复部分 | 仍是原Operation，不重新派生相对位移等意图 |
| 确认原操作完成后进入后继 | 领域证据支持完整输出，正常完成当前控制出口 | 提交/推进最多一次，不能伪造成功 |
| 从恢复入口重做某段 | 处置使原意图/输入失效，需要重新执行上游步骤 | 经过恢复计划建立新的执行代次/相关操作，保持明确的工件归属 |
| 重做当前迭代 | 重建当前循环体执行，但不是推进到下一件 | 保留迭代业务身份，替换本轮执行代次 |
| 结束本轮走排废等业务路径 | 明确工艺结果与后续去向 | 不能靠随意Skip完成Join或伪造检测结果 |
| 终止本Run并重新启动 | 旧Run不可复活，新Run重新准备 | 是否仍处理原工件和复用业务去重键须明确 |

节点内部的阶段继续由操作实现封装，引擎不直接修改节点的内部阶段；跨节点回退由运行时恢复计划管理。

### 示例：处理后必须重新定位，但不能重复取料或记账

```text
进料 → 定位 → 移动 → 取料 → 检测 → 记录 → 出料
```

检测异常后，人工可能只是清洁镜头，也可能移动了工件、把工件放回源位，或者更换了一件工件。三者不能使用同一个无条件“重试”。

- 只清洁镜头：如果原图已不可用，需要重新采集/检测，旧图与派生结果失效；不重复进料或取料。
- 移动了工件：原定位可能失效，需要从满足当前物料位置前提的定位入口重新运行，不能沿用旧坐标结果。
- 工件仍在夹爪中：回到取料之前的入口不具备进入条件，除非先执行明确放回/交接处置。
- 已把工件放回：核实物料身份和位置后，建立新的取料操作；旧取料曾成功的历史不能伪装成从未发生。
- 更换了工件：属于工件上下文切换，不能作为原工件第7轮的普通Retry；明确结束原工件并开始新业务实例。
- 已写入记录：从检测重跑不能默认再插入一次记录，需领域决定沿用去重键、追加复检记录或明确纠正旧记录。

### 恢复入口，不是任意NodeId

设计者应声明允许的恢复入口及其前提；编译器校验结构，运行时校验现场。恢复目标标记只说明“可被考虑”，不证明“现在可进入”。

运行时先生成不产生外部副作用的候选恢复计划：

1. **控制范围**：回到哪里，影响哪个迭代/Block/并行Scope，哪些执行必须先停止。
2. **前置处置**：资源、物料、设备状态、参数和原意图需要哪些核实/修复。
3. **重跑步骤**：哪些节点重新运行，哪些已完成操作允许保留，哪些副作用必须补偿或去重。
4. **数据策略**：哪些派生数据失效、哪些输入必须重建，哪些历史事实只保留审计不可再绑定。
5. **退出与失败策略**：恢复步骤失败停在哪里，是否仍可处理，如何停止。

计划验证成功后由操作员确认影响，再在执行前重新核实条件和会话版本。展示计划不等于已经授权执行；状态改变时必须重算/拒绝，而不是执行过期预览。

### 回退与循环

- 当前第7轮回到本轮入口：仍处理第7件，不能再次经过正常Loop计数逻辑变成第8轮。
- 不能直接回到第6轮：上一件可能已经离站、记账或被其他设备接收；应作为显式返工业务，而不是普通流程回退。
- 内循环回到外循环入口：关闭/替换受影响内循环帧，明确保留哪一个外循环工件身份。
- 重新执行的数据归属到新的本轮代次；第7轮旧分支结果不能满足新代次的绑定或Join。

### 回退与并行

- 回到A分支内部：只有B结果仍有效、资源隔离及进入条件成立时，才保留B；新A与被明确保留的B属于同一被验证的恢复方案。
- 回到分叉之前：影响整个并行组，必须审查所有已完成分支的副作用，不能自动全部重发。
- 恢复代次变化时重建Join资格；旧到达消息不能再次计数。
- 不能从A分支直接跳入B内部，或跳到Join伪造所有分支完成。

### 回退与Block

- 默认只允许在当前活动调用路径内的合法恢复入口间选择。
- 回到父流程并重做Block时，先结束旧子运行、隔离旧输出，再创建新的子运行；不能同时保留两个相同业务调用在执行。
- 不能跨到一个无关子文档内部，绕过其输入映射与入口条件。

### 数据不是全部清空，也不是全部保留

- 局部派生数据：按受影响依赖与执行代次失效，重新生成。
- 原始输入：由计划明确固定、重新获取或重新确认。
- 公共共享数据：不能一律恢复旧值，其他分支/外部系统可能已经合法更新。
- 已提交外部副作用：不能靠删除NodeOutputs撤销；走领域补偿、核实或去重。
- 历史诊断与事实保留，但从当前执行绑定可见集合中排除失效数据。

### UI必须说清楚这次“继续”会做什么

例如：

```text
恢复入口：本轮重新定位
业务对象：第7件 / 产品P007
需要核实：工件已位于检测夹具，机器人不再夹持
将重跑：采集、定位、检测
不会重跑：进料
旧数据将失效：原图、原定位、原检测结果
记录策略：沿用本业务去重键，或按已配置的复检规则追加
```

如果无法给出可靠的计划与前提，选项应禁用并解释原因，仍允许核实、处置或停止。不是让操作员猜测任意Jump的后果。

## 7. 并行恢复的第一版范围

当前引擎并行分支异常会取消同伴并等待WhenAll，随后明确拒绝Scope内Retry/Jump；这是已存在的安全保护，不能通过删除判断来开放恢复。

第一版建议：

1. 捕获故障后保留受影响Scope、分支位置、Operation和Join状态，不让根运行立即销毁现场。
2. 默认阻断整个所属并行Scope的新调度，不默认所有其他分支可继续。
3. 记录每个分支是运行中、等待、已完成、中断未确认还是故障。
4. 相关分支静止/退出状态可确认后，才授权有资源与数据独立性证据的局部恢复。
5. 缺少独立性声明、不可恢复中断或无法确认停止时，只有核实、人工处置和终止等保守选项。
6. 不先实现任意跳转、任意回滚、多分支同时人工动作；先覆盖“独立分支、完整身份、单动作处置”。

处置等待应属于Token/Scope控制生命周期，不能继续依赖根RunAsync最外层catch改nextEntryNodeId。

## 8. 外部代码主动触发与清除条件

建议在宿主暴露UI无关的故障控制入口。以下仅表达语义，不是现有API：

```csharp
var receipt = await faults.RaiseFaultAsync(new ExternalFaultRequest
{
    SourceKey = "PLC/StationA/GuardDoor",
    ConditionKey = "DoorOpen",
    Target = stationScope,
    StopMode = ControlledInterrupt,
    Message = "安全门已打开"
}, cancellationToken);
```

它必须真正阻断后续调度并启动处置，而不只是写日志。返回值首先说明“控制请求已接受”，**不能代表设备已经停止**。调度阻断、在途退出和设备停止确认通过会话状态/等待接口分别反馈。

### 请求语义

- 节点/Run级请求明确携带目标运行身份，禁止旧回调击中新Run。
- 持续工位/设备条件可在Idle时建立启动门禁，下一次Run也必须检查；它不是把旧Run故障直接复制到新Run。
- 来源身份、条件身份和条件发生代次用于去重与清除。PLC持续上报同一条件不产生无限弹框。
- 外部清除只清除自己拥有、且发生代次匹配的条件；旧Clear不能清掉新一轮故障。
- 调用方取消等待回执，不等于撤销已接受的故障请求。撤销/清除需要显式命令。
- 外部接口经过宿主授权；不能任意指定其他工位恢复或越权释放阻断。

### 解除语义

```text
PLC确认门关闭
→ ClearCondition(本次条件句柄)
→ 该外部条件已清除，但会话仍未批准恢复
→ 操作员请求继续
→ 引擎重新检查全部阻断、设备状态、输入和操作有效性
→ 合法才继续
```

条件A清除不能移除条件B；故障会话关闭不能移除独立人工Pause。若允许某类临时非安全条件自动续跑，应作为明确的特例策略配置，不作为所有异常默认行为。

## 9. 统一动作协议与人工作业台

每个动作都包含稳定ID、语义类别、说明、风险、是否可用、不可用原因、必要确认/参数和执行入口。客户端发CaseId、Revision、ActionId、请求幂等键与操作员身份，服务端重新验证，不相信客户端缓存的IsEnabled。

通用动作可以是：重新核实、继续原操作、执行指定处置子流程、恢复本轮/检查点、按证据确认完成、上报外层、终止运行。并非每次故障都具备所有动作。

执行动作后明确返回：已处置但仍需验证、可继续原操作、确认完成且有有效输出、需建立结构化恢复计划、仍待处置、停止。确认完成不是忽略错误；不能生成缺少事实依据的标准输出。

界面使用一个故障处置工作台而非每个分支一个模态弹框：

- 定位到“工位/Block/第几轮/哪个并行分支/节点/哪次操作”。
- 展示受影响范围、在途操作、已完成动作和未确认设备。
- 优先展示建议动作、执行后影响、可能重复的副作用。
- 展示尚未解除的全部阻断条件。
- 点击后显示动作进度；动作失败回到同一会话并保留失败记录。
- 所有停止/恢复动作有授权、版本和去重检查；一组冲突资源不允许并发执行多个处置动作。

## 10. 恢复子流程的特殊执行权限

主流程被Recovery阻断时，不能把恢复子流程也用同一门锁死；但也不能让恢复子流程绕过门禁等安全条件。

应区分：

- 主流程普通调度许可。
- 当前会话的处置动作许可。
- 所有执行都必须遵守的宿主安全/设备互锁。

恢复子流程应作为受监管的子运行，拥有可见路径、取消、能力预检和资源生命周期。使用主流程保留的设备资源时通过会话授权交接/借用，避免保留租约导致恢复动作死锁，也避免任意释放租约允许其他分支抢占。

## 11. 故障与完成并发时的控制规则

- 只保留一个有权推进运行的控制协调入口，明确命令接受与结果提交的先后关系。
- 每个Operation最多一个活动尝试；旧尝试退出未确认时不启动新尝试。
- 结果、设备回调、人工动作都携带身份/代次，过期消息只作为诊断或晚到证据，不自动推进。
- 终止请求一旦接受，本Run不能再被普通恢复动作复活。
- 多故障必须全部满足各自解除条件，禁止一个Continue清空所有Hold。
- 检查点恢复要产生受验证的控制/数据恢复计划，不裸改程序指针。

## 12. 验收路径（待实施）

先用可控假设备和可控Task屏障，不靠Sleep制造竞态，覆盖：

1. 第7轮故障恢复仍属于第7轮，进料次数不增加。
2. 相对移动超时、实际已完成、再次处置不重发位移；取料和记录用真实任务/去重计数断言。
3. A失败、B成功，恢复A时B不重复执行，Join只放行一次。
4. A失败、B在途，未确认B退出前不得重建Scope或释放设备。
5. 两分支同时失败、同伴取消、外部门禁同时发生，原始原因保留且只解除相应阻断。
6. B等待A信号时，不因要求所有节点正常完成而卡死处置。
7. 外部故障与节点成功提交交错、旧响应到达新迭代、操作员重复点击均不重复推进。
8. 准备前/准备中/暂停中/恢复中/运行结束后的外部触发和条件清除。
9. 处理子流程自身失败或取消，原故障仍可见，资源和控制权不泄漏。
10. 任意代码不响应取消时，不伪装已经停止，不提前释放其资源。
11. 从前序恢复入口重跑后，原定位/测量失效，原工件身份与应保留的业务去重键正确；不重复取料、进料或记账。
12. 循环体入口重做不多计轮次；父Block重做不遗留旧子运行；跨并行结构的非法目标拒绝。
13. 恢复计划展示后现场状态改变、旧结果/旧Join到达、重复恢复提交，均不能执行过期计划或多推进一次。

先实现串行/结构化循环与外部中断闭环，再开放受限并行恢复，最后扩展结构化检查点恢复。不是先画出所有按钮再补安全逻辑。

## 13. 对现有实现的具体改造方向

- 保留Document/Plan/BoundPlan/Handler/Token体系，不新建第二套调度引擎。
- 将故障拦截从单纯根路径catch扩展到具体操作/Token，保留恢复现场。
- 将根取消与可恢复尝试中断分开。
- 将外部字符串Hold补充为有来源、条件代次、影响范围和解除权限的故障/门禁记录；普通Pause独立存在。
- 以完整循环/并行/子运行身份支撑恢复和数据有效性。
- 将告警子流程纳入受监管执行，不仅是独立new Engine。
- 增加统一处置动作执行及服务端恢复验证；旧Retry/Jump只在安全语义映射明确后替换，不放宽保护来凑功能。

本设计不包含跨进程崩溃恢复承诺。若需断电续跑，必须另行设计持久化意图/检查点、设备状态核实与业务去重，不能依靠内存Operation实例。
