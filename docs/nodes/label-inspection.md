# 标签检测业务节点

## 已实现的首版

工具箱 **业务检测 → 标签检测**，节点类型 `LabelInspection.Inspect`。一个节点执行一张显式绑定的 `DP.Vision.ImageFrame`，直接调用 DP.LabelInspection 的无界面 `InspectionEngine`；不拆散、复制其逐 ROI 检测与判定规则。

- 输入：`Frame`（必需绑定）、可选 `CycleId`（固定值或绑定）、`TaskData`（绑定或空）、可选 `LabelCoordinates`（标签坐标系，见下文“标签定位”）。周期不默认等同流程 RunId；任务数据的周期/有效期仍由 SDK 检查。
- 配方：固定模式使用节点内 `RecipeJson`；填写 `RecipeCatalogPath` 后按本次 `RecipeKey` 输入选择完整外部版本，详见下文。两者均使用 SDK 原生格式，保留检测项目、字段约束、异常设置及库 ID/Revision。不将运行图像、TaskData、引擎或报告写入节点配置。
- 输出：`WorkflowLabelInspectionResult`，包含输入 `FrameId`、`CycleId`、配方名称/内容摘要、资源快照摘要及完整 `InspectionReport`；目录模式另有 `RecipeId`/`RecipeVersion`，`RecipeJson`记录实际运行规则供报告显示。`Verdict`、`IsQualified`、`Regions`、`ElapsedMilliseconds` 是 SDK 报告的转发，不自行推断“全部必检已完成”。下游可以绑定 `Verdict` 或 `Report.Verdict`。
- 默认有效报告无论 Ok/Ng/Review 都经 **Success** 继续；Success 仅表示节点返回了报告。报告内的阻断/阶段失败仍完整保留；外层决定是否转人工。绑定、输入尺寸/布局、资源加载失败或无法返回报告才是节点故障。取消不发布报告。
- 开启 **“NG走失败出口”** 后，判定不是 Ok（Ng 或 Review）时报告照常提交，并沿 **Failed** 出口继续，失败支路可直接绑定本节点的 `Verdict`/`Report`。“失败”出口默认不显示，需在“输出端口”中启用并连线；未连线时本路径到此结束（运行仍正常完成）。节点故障在“失败”出口已连线时同样走这条支路，但没有报告输出。

## 使用

1. 上游放置文件/相机图像节点，将其 `ImageFrame` 绑定到标签节点的“输入图像”。生产图像不取自配置页样张。
2. 配置“资源根目录”。相对路径基于当前流程文件目录；未保存的流程基于宿主目录。其它资源路径必须位于显式根目录内，可以使用根内绝对路径或相对路径。不回退到开发机资源目录，不自动联网下载。
   **OCR路径示例**：已有模型位于`C:\Data\PiProgects\WorkFlow\models\ppocr_rec.onnx`时，这只是原始文件位置。若节点资源根是`D:\LabelResources`，应先复制为`D:\LabelResources\models\ppocr_rec.onnx`，再将“OCR识别模型”填写为`models/ppocr_rec.onnx`；不能直接引用根外绝对路径。配置页打开/重载前会非异常式检查路径，错误显示实际根和复制说明，状态栏悬停可查看完整信息；保持窗口可修改，修正后点“重载资源”。不会自动复制模型、扩大资源根或修改已保存的路径；生产仍拒绝越界与子目录链接。
   **内嵌字典要求**：当前`OnnxTextLineRecognizer`读取ONNX的`character`元数据，不自动读取相邻txt。工作目录原始`models/ppocr_rec.onnx`缺此项；已生成图/权重不变的`models/ppocr_rec_embedded.onnx`兼容副本，复制到节点资源根内后使用`models/ppocr_rec_embedded.onnx`。转换入口为`DP.Vision/tools/embed_ocr_dictionary.py`，完整类别字典使用`--format ctc-labels`（首行为CTC空白占位`#`、末行为ASCII空格），仅将中间字符嵌入；不能整份字典直接嵌入、去重或重排。真实.NET加载及合成`ABC123`识别已验证，不代表生产精度验收。目录模式使用新路径发布新配方版本并刷新目录，不覆盖旧资产。
   **最新官方V6候选（CPU优先试small）**：PP-OCRv6随PaddleOCR 3.7.0于2026-06-11发布，已有PaddlePaddle官方直接发布的ONNX。工作区`models/ppocrv6-small-rec/ppocrv6_small_rec_embedded.onnx`由官方small识别ONNX添加匹配的18,708字符元数据得到；原始文件保留，官方LFS大小/SHA256校验通过，图和权重未改。不能复用V5字典（V6输出18,710类）。真实DP.Vision .NET路径8组中文/标点合成测试全匹配，本机首行约74毫秒、后续约17–39毫秒；尚未验收用户实际失败样张。来源、固定revision、摘要、转换命令见模型目录README。复制到显式资源根内，OCR路径填写`models/ppocrv6-small-rec/ppocrv6_small_rec_embedded.onnx`，重载后应用；目录模式发布新版本并刷新。SDK已另行扩展单字符参考与显式等格规则质量到中文/标点/符号，每库最多4096字及1600万参考像素；重建后使用，不能以升级识别模型代替制库/绑定修订，也不自动接入det整图检测。

   **此前可追溯服务器版候选（非最新）**：`models/ppocrv5-server-rec/ch_PP-OCRv5_rec_server.onnx`为PaddleOCR官方PP-OCRv5_server_rec模型系列的RapidOCR v3.9.2公开ONNX转换文件，并非Paddle官方直接发布的ONNX。文件SHA256已匹配发布清单，18,383个内嵌字符与官方inference.yml顺序完全一致；来源、许可及验证见该目录README。复制到资源根内、更新识别路径再重载；目录模式发布新版本。旧小模型与此候选均通过8组中文/标点合成测试；单字符参考字库和等格规则质量现已支持精确Unicode单字，包括中文/标点，但仍须人工制库和显式绑定修订。该服务器版在本机当前CPU设置下每行约1.4秒，旧小模型约20–75毫秒，因此保留旧文件、不自动改已有流程，真实失败样张需对照诊断后再决定替换。
3. “字库/模型库目录”是 SDK 数据根目录，包含原来的 `libraries/`、`anomaly-libraries/` 等结构；不要只复制 recipe.json 就认为完成部署。必须带上配方使用的准确库 ID/Revision 和模型文件。
4. 新建节点还没有配方时不阻止流程编译运行：先运行一次流程，上游采图/定位照常执行并产生预览，执行到标签节点时报“尚未配置配方”（不准备资源，可走“失败”出口）。然后打开节点窗口：在参数页“导入配方”，或点图像上方“载入上游预览”（或参数页“加载配置样张”）后在图上画 ROI，并在左侧“ROI规则”页设置项目与约束。没有图像时页面也会先接上字库/异常库管理，并在状态栏给出下一步。模板模式填写“参考图”；自由模式不加载残留参考路径。纯空白检查不强制安装 OCR 模型。
5. 编辑后的完整配方在“应用/确定”前捕获到隔离副本，保持原配方名称，随后一次性提交，可整体撤销；取消不回写。JSON 可在没有预览时导入并保存。
6. 修改资源参数或外部参考后，用参数页“重载资源”重新装配独立试检测引擎。生产启动只登记配置，首次执行标签节点才详细加载；后续调用按文件大小/修改时间判断缓存失效，单次检测始终持有完整快照，不要求重新确认制作签名。固定节点内配方JSON/资源根/索引路径仍是冻结配置，修改需重新编译运行；目录模式的配方选择来自任务输入，发布新版本后显式刷新生产目录即可用于后续任务。
7. 正式运行后打开节点窗口即显示本次运行：同一帧图像（有放置时对齐到配置帧）、ROI 框与缺陷标记，图像下方为分组证据、单字与条码明细；也可随时点图像上方“显示运行结果”。试检测结果显示在同一位置，但不进入正式输出；输出失效后不再显示该次运行。

原生“多图制库”支持同图最多32个独立单行制作ROI，可连续框行、用区域选择器逐条提取或“提取全部ROI”；每行保存独立人工文字和提取状态，表格/清单标明来源ROI。重提/调整/删除只作用于所属区域；失败、零候选和取消不清除旧候选，批量失败继续下一行。换图清除当前制作区域和候选但保留已核对清单。制作ROI不是自动加入配方的检测ROI；识别后可直接修改表格单字并选择加入清单，不要求额外字符确认。无需先载入主工作台样张，已装配的编辑提取服务也会连接到字库窗口。仍需保存新字库修订并显式绑定。详见SDK `QUICK_GLYPH_LIBRARY.md`。

逐字符异常模型B现已贯穿支持中文、标点、符号及补充平面单字。批量训练需为同组良品框一致边距的稳定文字行ROI，提取后直接修改表格并选择样本，训练发布新库修订，再显式绑定配方。纯标点无需ASCII锚点；缺模型仍NG，A参考不会自动成为B模型。旧ASCII模型保留历史墨迹行几何，新Unicode/ROI模型为库schema v2，旧SDK拒读，须重新生成宿主及依赖。目录模式还需发布更高配方版本并刷新；详见SDK ADR-0003。

配置工作台中的“发布字库/异常库修订”、导出文件是明确的外部写入，不随节点取消/撤销回滚。新发布的库修订也不隐式替换配方原有固定修订。

## 单节点按本次任务选择配方

- 留空“配方目录索引”即原固定模式；填写根内索引（如 `recipes/index.json`）启用目录模式。“本次配方”可绑定上游任务的字符串成员，也可填固定字符串。`A`选择**本次开始时目录中的最高版本**，`A@3`精确选版本3；ID区分大小写，不含`@`/控制字符，最多128字符，版本为正整数。空/未知ID或版本故障，不沿用上一帧、不回退内置配方。
- 推荐上游一次性捕获任务中的配方键、CycleId、TaskData，与本帧使用同一任务关联。不是先改全局当前配方、再等图像到达；示例任务文件只演示此语义，不是MES协议。
- 启动读取索引最多1MB/4096个版本，不读取每套详细JSON、参考、库或模型。选择后才读取所选描述（最多2MB）、校验摘要、详细装配并取得租约。加载、排队及检测期间固定该版本；目录刷新不影响在途调用。
- 完整描述 `WorkflowLabelRecipeProfile` 包含ID/版本、原生RecipeJson、根内数据目录/参考/OCR/CNN/作者样张路径、活动参考/模型SHA256及该配方的参考位姿。目录模式不使用节点草稿的参考位姿或资产参数装配生产资源；Frame、任务输入、当前定位和NG出口策略仍由节点/请求决定。
- `WorkflowLabelRecipeCatalogStore.PublishAsync(root, indexPath, profile)`捕获活动资产摘要，不加载推理引擎、不复制资产；先写完整描述，再原子替换索引，跨进程文件锁协调发布。不同内容不能覆盖同一ID/版本，相同内容可重复发布；从索引删除条目不解除历史快照的版本占用。取消/故障可能留下未入索引的孤立快照，仍需增加版本号发布不同内容。发布不是一键部署包。
- **已发布版本资产保持不可变**：新参考/模型使用新路径（推荐版本目录），库使用准确ID/Revision；冷加载核对参考/模型内容。不要原位覆盖旧版本引用的资产，也不要删除/改写历史描述；缓存中的旧完整快照仍可继续使用。保留文件大小/时间戳不变的模型覆盖仍受原有模型别名缓存限制，发布须使用新路径或更新时间戳。
- 宿主显式调用 `ReloadRecipeCatalogAsync(root, indexPath)` 刷新元数据，无文件监听；刷新失败保留旧目录，同ID/版本内容变化拒绝刷新。宿主记录最多8192条该目录历史版本身份。刷新后的后续任务可以选择新版本，不必停机修改节点；`ID@版本`不会自动升级。已有目录不会在每轮准备自动重读。
- `PrewarmRecipeAsync(root, indexPath, key, maximumParallelRois)`提前装配生产**同一缓存**，执行预算须与节点一致；不检测、不提交报告、不修改任务选择。仍受容量/加载并发限制，暖缓存可被TTL/LRU淘汰。
- WinForms参数页“5. 配方目录”：载入目录版本到隔离编辑草稿、显式发布新版本、刷新生产目录、预热指定版本。**应用/确定不等于发布**；载入草稿不改任务选择绑定。发布/刷新/预热是外部副作用，不随取消编辑回滚；首次发布可以初始化空的固定选择，已有绑定保持原样。
- 目录正式报告按实际版本JSON/位姿显示，只读且不装配草稿模型、不把报告ROI回写草稿；编辑/试检测先载入目录配方或配置图。配置页仍使用独立试检测引擎，不计入生产缓存。WPF可通过通用属性配置目录/绑定，未添加同等的目录发布工作台。

## 标签定位（复用流程定位，ROI 随动）

定位不在标签节点内重做，而是复用流程已有节点：

```
图像获取 → 模板定位（旋转/尺度） → 构建本帧坐标系 → 标签检测（标签坐标系 = 坐标系节点.CoordinateSystem）
```

- **原图进入，ROI 随坐标系变换**：节点输入始终是整张原图，不做整图摆正。配方 ROI 直接画在**配置帧的原图**上；配置时记下这一帧的定位作为**参考位姿**（坐标系的局部→原图矩阵，随节点保存）。
- 每帧放置 = 本帧局部→原图 × 参考位姿的逆，即 ROI 跟随标签相对配置帧的位移、旋转和缩放；配置帧本身为恒等。节点把这个仿射作为放置（`InspectionPlacement`）交给 SDK。
- SDK 只对每个 ROI（外扩 16 像素）按放置从原图取出该区域交给检测/识别，不变换整张图。纯平移（整数像素）时直接取像素，不插值；只有标签有旋转/缩放时才对 ROI 小块重采样，使文字/码在 ROI 内保持配置时的方向。ROI 放置后超出原图时节点故障（可走“失败”出口）。
- 绑定了标签坐标系但还没有参考位姿时节点故障，提示先在配置页“载入上游预览”。
- 本帧没有定位结果（例如模板未找到）时节点故障，不沿用其它帧的坐标系。
- 未绑定时保持原行为：配方坐标即原图坐标，输入图须与配方同尺寸（错误信息会给出两者尺寸）。
- 配置：先运行一次采图与定位，在配置页点“载入上游预览”。还没有配方时：原图原样载入，本帧定位记为参考位姿，直接在原图上画 ROI（配方尺寸即原图尺寸）。已有配方时：不改参考位姿，把本帧按定位对齐到配置帧显示，便于核对 ROI 是否仍落在标签上（对齐后超出原图的部分为黑色）。记录参考位姿要求“标签坐标系”直接绑定定位节点的 `CoordinateSystem` 成员；绑定坐标系时请用“载入上游预览”作配置图，手工加载的样张没有定位结果。
- 模板模式的参考图就是配置帧原图：载入后在参数页点“保存为参考图”，保存为资源根目录下 `label-reference-<节点ID>.png` 并填入“参考图”；目录模式追加唯一样本标识写入新文件，避免覆盖已发布版本的参考。
- 报告坐标为配置帧原图坐标；配置页显示运行结果时把本帧按放置对齐到配置帧，ROI 框、证据和字块直接叠加；`WorkflowLabelInspectionResult.Placement` 供下游换算到本帧原图。
- 放置时推荐“假定已对齐”；“平移配准”只用于边距范围内的残余偏移。双线性重采样对逐像素差异/清晰度类指标有轻微影响，建议缩放接近 1。
- SDK 侧契约见 DP.LabelInspection 的 `docs/node-packaging/04-placement.md`。

## 界面

WinForms 节点窗口与其它视觉节点一致：

- **右侧图像**：上方工具栏为“载入上游预览”“显示运行结果”、新建 ROI 类型下拉（空白/文字/条码/一维条码/二维码等）、“选中/调整”、“适应窗口”“1:1”、“开始检测”“取消”；图像下方为判定条、检查证据及缺陷标记/单字明细。在图上左键拖动按所选类型新建 ROI。
- **左侧分页**：参数 | ROI规则 | 运行结果。
  - 参数页除节点属性外有五组按钮（生产缓存/目录宿主可选接入）：“1. 配方与样张”（加载配置样张、保存为参考图、导入/导出配方、重载资源）、“2. 字库与模型”（“字库…”打开单字库与多图制库两页的窗口；“异常模型…”打开模型库与批量训练两页的窗口，关闭时可把新发布版本绑定到ROI）、“3. 检测设置”（检测阈值、试检测任务数据）。
  - ROI规则页为 ROI 列表及所选 ROI 的类型、检测项目和规则，可绑定字库/异常模型库，并提供字段绑定、采用探索文字ROI、清空ROI。修改即时生效（无效组合如名称重复不会写入并在说明区提示），与其它参数一样在“应用/确定”时提交、“取消”放弃。画布上新建或调整 ROI 后列表自动刷新，画布选中的 ROI 同步选中。
- 不再提供“参考模式”手动开关：填写“参考图”即模板模式，留空为自由模式；新建配方默认按已对齐处理（ROI 随标签坐标系放置）。
- 深色主题统一应用到 SDK 工作台、ROI 规则页及其弹出窗口。
- “加载配置样张”可选资源根目录外的图片：自动复制到根目录下 `samples/`（同名同内容复用，内容不同追加序号，不覆盖），配置样张路径记录为相对根目录的路径，属性页同步刷新。

## 资源与生命周期

`WorkflowLabelInspectionRuntime` 实现事务式**轻量配方登记**：递归登记根/子计划的配置快照，不解码参考图、不读取库内容、不加载ONNX。登记提交后按绑定作用域和计划路径查找；准备失败/取消不发布登记。未选中的配方分支不会详细加载，也不会因为其缺失模型而阻止其它分支启动。

**按需加载与缓存**：执行到标签节点时才捕获参考图、当前ONNX和活动固定库修订。模型复制为临时快照；字库/异常库通过不可变仓交给引擎。同一配方版本的并发首次请求合并为一次加载；单个等待者取消不取消其他等待者共同需要的加载。加载失败不发布半成品、不提交检测报告，可再次重试。详细资源错误现在发生在标签节点，可按节点故障/失败支路处理，而不是启动时阻止上游采图。

固定模式的配置指纹包含配方JSON、路径、并行配置以及活动参考/模型文件的大小和修改时间。调用时检查，指纹不变就复用；同一计划位置的新版本替换旧缓存，旧在途租约仍有效。自由模式不把残留参考路径纳入指纹。已发布的库修订视为不可变，不自动升级。此原型不检测“内容被修改但大小和修改时间完全保留”的覆盖；发布资源时应改变版本/路径或正常更新时间戳。

**跨节点模型共享**：模型按内容SHA256、角色和固定CPU推理配置共享；相同内容的不同路径也可共享。OCR和异常骨干各用单实例，完整算法调用串行化；固定模式配方资源各节点独立；目录内相同完整版本/执行预算可共享串行引擎，不同配方/版本的参考、库快照、位姿与结果独立。输入、放置、任务和报告始终按请求独立。SDK借用装配入口不会释放外部模型。配置页仍创建独立试检测引擎，不计入生产缓存，也不与生产共享。

**清理与数量限制**：默认空闲24小时、每分钟检查、最多8份配方资源、4份不同模型、同时2个详细配方加载。检测/排队任务持有调用租约；运行登记不会永久占住重资源。过期时清理闲置资源，数量超限时LRU淘汰闲置资源；模型名额紧张时先清理闲置配方以归还模型。已退役但仍在用的旧版本也占加载名额。全部在用或加载时明确拒绝新的冷加载，不无限排队/扩容。模型最后使用时间不因配方稍后淘汰而延长另一整天。

通过构造参数`WorkflowLabelInspectionCacheOptions`设置策略；`CacheStatistics`提供登记数、缓存数、实际加载/命中/淘汰计数；`CleanupIdleResources(true)`主动清理闲置缓存。WinForms示例在标签参数页增加“4. 资源缓存”的查看/清理按钮，操作影响生产宿主，不随取消编辑回滚。登记数在运行结束后归零，但闲置缓存继续保留到期限/淘汰/宿主关闭。数量限制**不是进程内存字节硬预算**，参考图、报告、原生工作区和配置页另占内存；未实现多实例池和字节预算；任务配方选择/目录/发布/预热已接入下文新版演示。临时副本删除失败只记录警告。

同一节点的引擎在一轮内复用，排队调用串行，内部 ROI 按“最大并行数”执行。请求在异步等待前 Retain 实际图与参考图；退役等待所有在途/排队调用退出后释放模型。关闭配置窗口会先异步取消并等待试检测，再释放控件和页面引擎，避免在 UI 线程同步等待造成死锁。

配方最多 1MB、128 个 ROI；输入 Gray8/Bgr24，沿用 SDK 的 16M 像素限制。模型文件各最多 256MB，参考/样张编码文件最多 64MB。帧/预览使用原有 Workflow 图像仓预算。完整报告可能包含字块和差异像素；首版没有额外的永久报告历史仓，长循环需由宿主明确输出保留预算。

预览目前沿用仅 NodeId 的帧仓，标签节点 ID 不能跨子计划重复；准备阶段明确拒绝，不混合不同节点的图像。执行资源本身按计划路径隔离。

## 宿主装配

工程与内核隔离：

- `Nodes/DP.WorkFlow.Nodes.LabelInspection`（net8.0）：模型、报告包装、Handler、Runtime Module；无 UI/原生实现依赖。
- `Hosting/DP.WorkFlow.LabelInspection.Runtime`（net8.0-windows）：SDK 资源、引擎和运行租约。
- `Studio/DP.WorkFlow.LabelInspection.UI`（net8.0）：配方捕获/提交桥和页面模型。
- `Studio/DP.WorkFlow.LabelInspection.UI.WinForms`（net8.0-windows）：原生工作台页面（图像工具栏、ROI规则分页、参数页操作按钮，运行结果显示在图像下方）。

先注册 `WorkflowLabelInspectionModule`，再 Freeze 目录。宿主注册 `IWorkflowLabelInspectionService`、`IWorkflowLabelRecipeInspectionService` 和事务式运行准备链，例如：

```csharp
var labels = new WorkflowLabelInspectionRuntime(WorkflowDirectory, frameScope);
var algorithms = new WorkflowVisionAlgorithmBindings(algorithmRuntime, labels, Resources);
services.Add<IWorkflowLabelInspectionService>(labels)
    .Add<IWorkflowLabelRecipeInspectionService>(labels)
    .Add<IWorkflowRunPreparationService>(algorithms);
// 原有算法绑定/能力提供器及帧仓/根运行所有者注册保持不变。
```

桌面通过 `LabelInspectionWinFormsExtension { BaseDirectory = WorkflowDirectory, FrameSource = frameScope, CacheRuntime = labels }` 注册页面。停机先等待运行结束，再 `await labels.DisposeAsync()`；不在后台宿主加载 WinForms 程序集。

当前 WinForms 示例已直接注册节点模块、运行能力和页面，不需要额外安装 plugin.json。可移植节点程序集也导出独立 Runtime Module，但单独复制节点 DLL 不会自动创建宿主能力；外部插件部署应完整提供契约依赖，并让宿主/加载会话共享标签节点及报告契约程序集。
