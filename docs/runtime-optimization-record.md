# 底层优化项讨论记录

本文记录对 DP.WorkFlow **底层**（编译、执行、数据流转、运行观测）的优化项讨论。目标是先让底层的数据流转正确、可观测，再考虑 UI 怎么展示；UI 层问题暂不在此讨论。

讨论方式：按类别逐类讨论，每一项先记录现状和证据，讨论后再填写结论。**本文只记录，不改代码**；某项确认后，再单独立项实施。

## 讨论规则

每一项包含：

- **现象**：实际发生了什么；
- **证据**：代码位置（`文件:行号`，以 main `d572537` 为准）或可复现的事实；
- **与既有文档的关系**：是否已有设计（`workflow-run-recording-design.md`）、评审条目（`architecture-final-summary.md` 中的 AR-xx）或决策（`decisions/`）；新建议如与已接受的决策冲突，必须明确写出，不能悄悄推翻；
- **方案选项**：列出可选做法及其代价；
- **倾向**：我的建议（可被讨论推翻）；
- **待定问题**：需要你决定的事项；
- **结论**：讨论后填写。

状态取值：`待讨论` / `已确认` / `暂缓` / `否决`。

## 类别与讨论顺序

| 序 | 类别 | 关注点 | 状态 |
|---|---|---|---|
| 1 | 运行事实与记录 | 一次运行中发生了什么、记在哪里、几份记录是否一致 | 已讨论 |
| 2 | 数据流转 | 输出的存取与可见性、输入解析、变量与公共数据等旁路 | 已讨论 |
| 3 | 执行模型 | 子运行、两种循环、并行、多个执行入口 | 讨论中 |

| 7 | 节点定义与配置 | 定义分散、版本升级、可变配置与反射快照 | 待讨论 |

先讨论第 1 类，是因为第 2～5 类都要依赖"运行中发生了什么"有一份可靠的记录。

## 第 1 类：运行事实与记录

### 背景：现有设计的原则

`workflow-run-recording-design.md` §5 已确定三层结构：

- **运行工作集**（引擎内部状态）是执行的权威；
- **快照投影**只复制当前可观察状态，大小受"静态节点数 + 当前并行度 + 活动子流程数"限制；
- **运行记录器**分配事件序号、维护内存最近窗口、向宿主配置的 Sink 推送；**记录链路故障必须可诊断，但不能改变执行结果**。

这个原则是对的，本类各项都在它之内讨论。

> 更正：我在前一次总体讨论中提出"以事件流作为唯一事实来源（快照由事件折叠得到）"。对照上述原则，这等于让记录链路成为执行的一部分，与"记录失败不影响执行"冲突，代价也偏大。下面 R1-01 改为在现有原则内的方案，"完全事件溯源"仅作为备选列出。

### R1-01　同一事实写入多处，彼此没有对齐机制　`已确认`

**现象**　同一个状态迁移被分别写进几个互不关联的地方，没有共同的序号把它们对上。快照说"已完成"的节点，轨迹或持久化记录里可能没有对应事件，而任何一方都无法发现这种不一致。

**证据**

- "节点开始"一件事连续写四处：`WorkflowEngine.Execution.cs:107-110`
  - `MarkNodeStarted`：写引擎私有字典 `_nodeRuntime`，快照由此生成；
  - `SafeInvoke(NodeStarted, ...)`：C# 事件；
  - `RecordRunEvent("NodeStarted")`：记录器事件流，轨迹和持久化由此而来；
  - `BeginNodeTiming`：另一套计时。
- `NodeCompleted` 事件里的耗时取自 `_nodeRuntime`（`Execution.cs:197`），而不是由事件时间戳算出，两边各算各的。
- 记录器写入异常被吞掉（`WorkflowEngine.Observation.cs:259`）。按设计这是对的，但设计 §7.4 要求的 `RecordingFailed` 事件没有实现（全仓 0 处），所以丢了记录也看不出来。
- 快照的 `Sequence` 是独立计数（`_snapshotSequence`），与事件 `Sequence` 无关，消费方无法判断"这份快照已经包含到哪条事件为止"。

**影响**　界面、轨迹、持久化记录三方可能各说各话。现场排查时无法判断是"没执行"还是"执行了但没记下来"。

**与既有文档的关系**　符合设计 §5 的分层原则；缺口在于没有对齐手段，以及 `RecordingFailed` 未落地。

**方案选项**

| 选项 | 做法 | 代价 |
|---|---|---|
| A | 维持现状，只补 `RecordingFailed` 计数和事件 | 小；能发现丢记录，但仍无法对齐 |
| B | 每次工作集状态迁移，在同一步里向**内存事件流**追加一条事件（同一把锁、同一序号）；外部 Sink 仍然尽力而为。快照携带"已包含到的最后事件序号" | 中；需要把迁移收敛到少数入口 |
| C | 完全事件溯源：状态由事件折叠得到 | 大；与设计 §5 原则冲突，不建议 |

**倾向**　B。内存事件流属于运行工作集的一部分（可靠、不吞异常），写外部 Sink 的部分仍可失败而不影响执行。这样既保持现有原则，又让"快照—事件"可以对齐、核对。

**待定问题**

1. 内存事件流写入是否允许失败？例如 Payload 编码出错时，是降级为摘要后照常追加，还是丢弃该条？我倾向前者。
2. 快照是否需要增加"最后事件序号"字段？

**结论**（2026-11-18）

- **不引入额外编号做对齐。** 以精确时间戳 + 上下文（哪次运行、哪个节点、哪一次执行）关联还原现场。
- **时间戳改用高精度时钟。** .NET Framework 4.8 下 `DateTime.UtcNow` 默认精度约 1～15ms，快速循环时前后记录可能时间相同。
- **记录原则：只记关键事件，避免过细日志。** 过细的日志会淹没关键信息，反而妨碍排查。
- **记录失败要让人看得到。**
  - 现状：内核已有 `WorkflowRecordingHealth`（已记录、丢失、写失败计数，最后错误及时间）和限频通知 `RecordingHealthChanged`，但宿主和界面都没有使用。
  - 做法：通过下面的"节点提示"展示。
- **新增"节点提示"机制。**
  - 每个节点有一个累计提示列表，存放**不影响引擎运行**的提示。记录丢失是其中一类，以后其他非致命提示也放在这里。
  - 引擎侧产出提示（节点、时间、类别、消息），作为运行状态的一部分供界面读取，不进入执行路径。
  - 界面在节点**右上角外沿**显示黄色角标（与失败的红色区分）；点击查看详情，确认后清除。
  - 超过一定数量后按清理策略处理（具体上限和清理方式待定）。
  - 无法归属到节点的提示（如成批写入文件或数据库失败、运行开始/结束等运行级记录），放在**画布右上角**，使用同一机制。

### R1-02　运行树没有统一的顺序：三套序号，子运行各自计数　`已确认（并入 R1-01）`

**现象**　判断"谁先谁后"没有一个可靠的全局序号。

**证据**

- 一次运行里有三个互不相关的计数器：
  - 节点徽标上的执行序号 `#n`：节点**开始**时递增，引擎字段 `_nodeExecutionSequence`（`WorkflowEngine.Observation.cs:179`）；
  - 输出序号：输出**提交**时递增，`WorkflowRunState._nodeExecutionSequence`（`WorkflowRunState.cs:155`），数据血缘的 `SourceOutputSequence` 用的是它；
  - 事件序号：由记录器分配。
- 每个子运行（子流程、循环块的每一圈）有自己的记录器（`WorkflowEngine.Run.cs:193`、`WorkflowEngine.Continuation.cs:121`），三套序号也都从 1 重新开始。所以在循环块的子画布里，`#n` 每圈都从头编号。
- 合并父子轨迹只能按时间戳排序（`WorkflowEngine.Observation.cs`，`GetTraceBatch` 中的 `OrderBy(Timestamp)`）。
- 本项目同时面向 .NET Framework 4.8（ADR-0022）。在 .NET Framework 上 `DateTime.UtcNow` 的精度通常只有 1～15.6ms，快速循环时父子事件时间戳相同的情况很常见，合并后的先后顺序不确定。

**影响**　
- 你需要的"回环时一眼找到最后执行、导致停机的节点"，在跨子运行时没有可靠依据；
- `#n` 与输出序号不是同一个数，把"第 n 个执行的节点"和"它用了谁的第几次输出"对应起来需要额外换算。

**与既有文档的关系**　设计 §7.2 明确"子 Run 使用自己的 RunId，Sequence 在单个 Run 内单调"，这一点保留不变。这里要补的是"运行树范围的顺序"，与该设计不冲突。

**方案选项**

| 选项 | 做法 | 代价 |
|---|---|---|
| A | 根运行持有一个运行树级的全局计数器，子运行的记录器共享它；每条事件在保留本运行 `Sequence` 的同时，带上全局 `Ordinal` | 小；一个 `Interlocked` 计数 |
| B | 不加全局计数，改为在父运行事件流中记录子运行的开始和结束（带子 `RunId`），靠因果关系排序 | 中；同一时刻父子交错的事件仍无法排序 |
| C | A + B | — |

**倾向**　C。全局 `Ordinal` 解决排序；子运行开始和结束事件解决"这一圈属于父节点的哪一次执行"。另外建议明确：
- UI 上的 `#n` 是用开始序号，还是改用全局 `Ordinal`；
- 输出序号与开始序号是否合并成一套。

**待定问题**

1. `#n` 的语义：按"本画布内执行开始的顺序"（现状），还是按"整个运行树的全局顺序"？在循环块子画布里，你希望看到每圈重新编号，还是全局连续编号？
2. 是否接受合并"开始序号"和"输出序号"？合并后，一次执行有唯一编号，输出直接引用这个编号。

**结论**（2026-11-18）　不引入全局编号。先后顺序靠高精度时间戳 + 上下文关联，见 R1-01。

遗留问题：循环块子画布里 `#n` 每圈重新编号，这一点转到第 3 类讨论两种循环的语义时一并确定。

### R1-03　事件缺口　`方向已确认（细节待定）`

**现象**　有些事件设计里要求了但没有实现；有些实现得比设计少；还有一些执行语义没有对应的事件。

**证据**（全仓检索事件键）

| 情况 | 事件 | 说明 |
|---|---|---|
| 设计要求，未实现 | `RunInterruptedDetected`、`RecordingFailed` | 0 处 |
| 实现少于设计 | `VariableChangesCommitted`、`PublicDataChangesCommitted` | 设计 §7.4 要求"Key 和值摘要"，实现只记了 Key（`Execution.cs:366`） |
| 未设计，缺失 | 并行开始（只有 `ParallelMerged`）、令牌分叉和结束 | 并行分支何时分开、谁和谁汇合，只存在于快照字典里 |
| 未设计，缺失 | 循环一圈确认 | 第几圈只能从执行身份里的 `LoopIteration` 推断 |
| 未设计，缺失 | 子运行开始和结束（在父运行事件流中） | 父子关系只能通过子运行事件里的 `ParentRunId` 反查 |
| 未设计，缺失 | 暂停、恢复、外部 Hold 增删、信号触发和等待 | 停机或等待的原因不在记录里 |
| 未设计，缺失 | 实际走的连线 | 见下 |

关于"实际走的连线"：`NodeCompleted` 已记录所选出口，配合执行计划本可以推出下一节点。但 `RunStarted` 没有记录流程的身份或版本（`WorkflowEngine.Run.cs:203`），离线拿到记录时不知道对应的是哪一版流程，也就推不出路径。

**影响**　事后复盘时，无法完整回答"为什么停在这里""当时在等什么""走了哪条分支"。

**方案选项**

- 按上表逐个补齐。
- 对"实际走的连线"有两种做法：
  - 每次跳转记一条事件（量较大）；
  - 只在 `RunStarted` 里记录流程身份（文档内容哈希或版本号），由离线工具结合执行计划推导路径。

**倾向**　
- 补齐表中"设计要求未实现"和"实现少于设计"两类；
- 新增并行开始、子运行开始和结束、暂停/恢复/Hold、信号这几类；
- 连线选择"`RunStarted` 记录流程身份 + 离线推导"，默认不逐跳记录；
- 循环一圈确认，等第 3 类统一两种循环的语义后再定。

**待定问题**

1. 变量和公共数据的"值摘要"是否有敏感数据或体积方面的顾虑？例如配方参数、图像引用。
2. 流程身份用文档内容哈希，还是由保存时递增的版本号？

**结论**（2026-11-18）

- 暂停、恢复、外部挂起（Hold）的增加和解除，以及节点开始等待信号或条件、等到或超时，**需要记录到流程记录中**。现状是这些都不记录（`WorkflowEngine.Control.cs` 中没有任何写记录的调用），停机后无法判断原因。
- 每类事件只在发生时记一条，平时不产生额外日志。
- 具体事件清单和字段（以及表中其他缺口），等第 2、3、6 类把数据流转、执行模型和文档模型的结构梳理清楚后再定。

### R1-04　观察者在执行线程上同步执行　`已确认`

**现象**　UI 等订阅方的处理逻辑直接在节点执行线程上同步运行。订阅方处理得越慢，流程跑得越慢。订阅方抛出的异常被吞掉，宿主无从得知。

**证据**

- `SafeInvoke(NodeStarted, node)` 在执行线程上同步调用（`Execution.cs:108`）；`NodeCompleted`、`NodeTrace`、`StateChanged` 同理。
- 有订阅者时，快照在执行线程上、在调度锁 `_stateSync` 内构造（AR-17）；子运行的快照还会逐层传给父引擎再发布一次。
- AR-17 阶段 1 只解决了"无订阅者不构造"。"每次迁移发布一次"已被测试 `SlowSnapshotObserver_IsExcludedFromSingleNodeExecutionTime` 写成契约。
- AR-19（观察者异常无诊断出口）仍未关闭。
- 上次"快速循环时界面卡死"的修复做在 UI 一侧（运行绑定节流、监视页合并刷新），引擎侧"同步通知"的结构没有变。

**影响**　生产节拍受 UI 订阅方影响；订阅方的故障不可见。

**与既有文档的关系**　ADR-0003 规定"事件观察者异常不得改变流程结果"，这一点保持。AR-17 指出：合并发布会改变一条已被测试固定的契约，必须显式设计，不能顺手改掉。

**方案选项**

| 选项 | 做法 | 代价 |
|---|---|---|
| A | 维持同步通知，只补 AR-19 的异常计数和诊断 | 小；节拍问题仍在 |
| B | 执行线程只更新工作集和内存事件流（R1-01 B），然后发出一个很轻的"有新序号"通知；订阅方在自己的线程上按需取快照或增量事件 | 中；需要改写 AR-17 那条测试契约，并说明新契约 |
| C | 独立分发线程 + 有界队列，队列满时按明确策略合并 | 中；多一个线程，要定义满队列策略 |

**倾向**　B（并补上 AR-19）。新契约可以写成："每次迁移都会产生一条事件，不会丢；快照按需构造，不再保证每次迁移都发布一次。"

**待定问题**

1. 有没有宿主（不是 UI）依赖"每次迁移同步回调"来做逻辑？例如设备联锁、MES 上报。如果有，它应当改为订阅事件流，而不是快照回调。

**结论**（2026-11-18）

- **执行线程不为界面做任何事。** 执行路径上不构造快照、不调用订阅方；执行线程只更新运行状态和记录，最多发一个很轻的"有更新"信号。
- **显示像视频一样按帧刷新。** 变化在引擎侧照常累积，界面按可配置的刷新帧率，隔一段时间在自己的线程上取一次整体状态刷新，不要求显示每一次变化。
  - 两帧之间一闪而过的状态（例如很快开始又结束的节点）可以不出现在画面上，完整过程以记录为准；
  - **最终状态必须显示**：运行停止、暂停、失败或进入等待时，界面要立即补一帧，保证停机时看到的就是停机那一刻的状态。
- **记录照常完整。** 每次状态迁移该记的事件一条不少，不受刷新帧率影响。
- **订阅方出错要看得见**（关闭 AR-19），通过 R1-01 的节点提示或运行级提示展示，不影响执行。
- **父子引擎同样解耦。** 子运行不再逐层向父引擎推送快照，父级或界面需要时再取子运行状态。
- 依据：现有订阅方只有界面（`WorkflowRuntimeHost.cs:458` → `WorkflowStudioRuntimeBinding.cs:40`）和父引擎转发（`WorkflowEngine.Children.cs:45`、`:238`），没有联锁或 MES 逻辑依赖这些回调。
- 实施时需改写测试 `SlowSnapshotObserver_IsExcludedFromSingleNodeExecutionTime` 固定的"每次迁移发布一次"契约，新契约为："每次迁移都产生事件，不丢；快照按需构造，界面按帧率刷新，停止类状态保证补一帧。"
- 默认帧率和是否允许按画面配置，留到第 4 类（观测接口，R4-b 统一节拍）一并确定。

### R1-05　没有默认持久化，现场事后复盘依赖宿主自行实现　`已确认（改为对外出口）`

**现象**　运行事件只保存在内存窗口里：每个运行最近 2000 条（`WorkflowExecutionOptions.MaxTraceEntries`），每个复合节点的子运行历史也最多 2000 条。程序关闭或窗口滚动后，记录就没了。

**证据**

- 仓库里只有 `IWorkflowRunEventSink` 接口和记录器，没有任何 Sink 实现（文件、SQLite 等均无）。
- 设计 §5 写明 Sink "可不配置（仅保留内存最近窗口）"，由宿主选择。

**影响**　"夜里停机、早上查原因"这类场景，如果宿主没有自己实现 Sink，就没有可查的记录。

**方案选项**

- A：维持现状，由宿主实现。
- B：在仓库里提供一个默认的本地滚动文件 Sink（例如按运行或按天分文件、JSON Lines 格式、带容量上限），宿主可以选择启用。
- C：B 加一个离线查看工具（读取文件、按序号回放、筛选），与第 4 类观测接口共用查询逻辑。

**倾向**　B，C 放到第 4、5 类讨论时再定。

**待定问题**

1. 现场是否允许写本地磁盘？保留多久、上限多大？
2. 是否已有 MES 或数据库方面的上报要求？如果有，默认 Sink 的格式最好与之兼容。

**补充现状**（讨论中核实）

- trace 与 Sink 由同一次 `Record` 产生：记录器分配序号和时间、编码 Payload 后，一份放入内存最近窗口（即 trace，`GetTraceBatch` 按游标读取），一份攒批（128 条或 100ms）由后台线程交给 `IWorkflowRunEventSink.WriteAsync`。待推送上限 4096 条，满了丢最老的；写失败只计入 `WorkflowRecordingHealth`。
- Sink 通过 `WorkflowExecutionOptions.Recording.Sink` 配置，每次运行（含每个子运行、每一圈）各有一个记录器，共用同一 Sink 对象。正式代码中没有任何地方赋值，只有测试实现过。
- 引擎回调与事件流重复：`NodeTrace` 把同一条事件在执行线程上再同步发一次；`NodeStarted`、`NodeCompleted` 与记录中的同名事件是同一件事。正式代码中 `NodeStarted`、`NodeCompleted`、`NodeTrace`、`RecordingHealthChanged` 均无订阅者。
- 现有 Sink 对外不友好：需实现两个 `ValueTask` 异步方法（.NET Framework 4.8 需额外引用 `System.Threading.Tasks.Extensions`）、按批接收、每次运行配置；事件无级别，说明文字在 `Data["Message"]` 中，接普通日志库需要每个使用方自己拼。

**结论**（2026-11-18）

- **定位：功能包只负责把想记录、想抛出的数据通过出口丢出去。** 外部想记录就接，不接就空着。功能包不内置写文件、写数据库的实现。
- **把现有 Sink 改为"两层出口 + 逐条回调"。**
  - **按流程的出口**：每个流程（宿主）一个，只出该流程的事件，其子流程、循环块每一圈都归到它名下；
  - **全局出口**：收全部流程的事件，每条带流程名；
  - 两层用法相同，可同时使用（例如各流程分开写日志，另在全局接 MES 上报）。
- **出口提供两种回调，外部接哪个都行：**
  - `OnEvent(事件)`：结构化事件，给数据库、MES；
  - `OnLog(级别, 一行文字)`：功能包拼好的日志行，直接转给 NLog、log4net 等。级别按类别对应：故障→Error，运行起止和节点开始/完成→Info，节点内部步骤→Debug。示例：`INFO [上料流程] 节点 拍照#3(第2圈) 完成，出口=OK，耗时 12.4ms`。
  - 可按级别或类别过滤；队列上限可配置。
- **保留的正确性要求（与外部形式无关）：**
  - 执行线程只投递，不等外部；后台线程按顺序逐条交给回调；
  - 外部回调慢时内部排队，有上限，满了丢最老的并计入"记录丢失"，通过节点提示（R1-01）显示；
  - 外部回调抛异常由功能包吞掉并计数，不影响流程，也不影响后续事件；
  - 同一流程内事件顺序不乱；多个流程并发时会交错，靠流程名和运行号区分；
  - 尽力送达：适合记录和上报，不适合联锁这类一条不能丢的实时逻辑。
- **事件需增加"所属顶层流程"标识。** 现状子流程事件只带子流程自己的名字（`WorkflowRunEvent.WorkflowName`），无法按顶层流程分出口。子流程事件归入顶层流程的出口，同时保留自己的名字和父节点信息（`ParentRunId`、`ParentExecution`）。
- **回调去留：** `NodeStarted`、`NodeCompleted` 保留；`NodeTrace` 等全部问题分析完再定；`SnapshotChanged` 按 R1-04 改为界面按帧率拉取。
- 默认文件落盘、离线查看工具不在功能包内做；如需要，在第 4、5 类再讨论是否提供示例。

## 第 2 类：数据流转

### R2-a　两种读取语义（按令牌可见性 / 取最新）　`已确认（不算缺陷）`

**现象**　读取上游输出有两套规则：

- 按令牌和作用域的可见性读取（ADR-0005）：`WorkflowRunState.TryGetVisibleNodeOutput`；
- 不看令牌、直接取最新值：`WorkflowBindingResolver.ResolveLatest`（`Data/WorkflowBindingResolver.cs:117`）。子流程对外输出用的是它（`Nodes.Composite/WorkflowSubflowRuntime.cs:38`）；编辑器单节点试运行用 `ResolveLatestInput`。

最初的担心是：子流程内部有并行时，"取最新"可能取到任意一个分支的值。

**核实结果**　在现有编译规则下不会发生：

- **WFB002**（`Core/Compilation/Analysis/Binding/WorkflowBindingAnalysis.cs`）：绑定来源必须在入口到消费节点的每条路径上都先完成，设计器候选列表也只列这类节点。因此并行兄弟分支之间互相绑定不了，只能绑并行之前的节点；局部回环中也绑定不到"后续节点"。子流程对外输出同样检查：来源必须在子流程结束前必然执行。
- **WF021**：每个并行必须有"全部到齐"汇聚节点；**WF022**：汇聚前各分支不能共用节点（`WorkflowParallelScopeAnalyzer.cs`）。
- 令牌只在运行启动（`WorkflowEngine.Run.cs:19`）和并行分叉（`WorkflowEngine.Parallel.cs:38`）时创建，循环不创建。没有并行时整个运行只有一张令牌，"按令牌取"与"取最新"结果相同。令牌可见性真正起作用的是"循环里套并行"（只读本圈汇聚后的结果）和故障恢复重跑（跳过已作废输出），是设计期规则在运行时的第二道保险。

**结论**（2026-11-18）

- 不算缺陷。子流程输出使用"取最新"是安全的，前提是 WFB002、WF021、WF022 三条编译规则成立。**以后如放宽这些规则（例如允许分支共用节点），必须回头检查这里。**
- 可选整理：子流程输出也改用按令牌可见性读取，全仓统一成一种取法。优先级低，暂不做。

### R2-b　取值时复制整份输出历史　`已确认（要做）`

**现象**　节点每读一个输入，`WorkflowRunState.TryGetVisibleNodeOutput`（`Execution/WorkflowRunState.cs:181`）都在锁内把**所有节点**的输出历史（`_nodeOutputHistory` 链表）整份复制成数组，再倒序逐条查找目标节点。

**核实**　历史不会随循环圈数增长：`CommitNodeOutput` 写入时会删掉同节点、同令牌、同作用域的旧输出（例如 `a b c d e c` 执行后链上是 `a b d e c`）；循环套并行时，作用域完成会清掉上一圈的分支输出。因此条数约等于节点数，单次开销为微秒级，目前不是瓶颈。另有一份"每节点最新值"表 `_latestNodeOutputs`。

注意：这里删的是**取值用的输出历史**；运行记录（trace / 对外出口）完整保留每次执行。

**结论**（2026-11-18）

- **改为按节点存、按节点取。** 输出表按节点分格（节点 → 该节点的输出列表），取值时只打开目标节点那一格，不再复制全部节点的输出。
  - 无并行时每格只有一份；循环套并行时，作用域完成前可能短暂有两份（上一圈 + 本圈），按令牌可见性选取；
  - 可见性规则和取值结果完全不变；
  - 与 `_latestNodeOutputs` 合并为一份数据。
- 改动集中在 `WorkflowRunState`。实施时机可与第 3 类中涉及该类的改动合并。

### R2-c　输入在节点执行过程中按需解析　`已确认（改为执行前取齐）`

**现象**　引擎调用节点执行代码后，由执行代码在需要时调用 `context.ResolveInput(node.Xxx)` 去上游取值（`Execution/WorkflowNodeExecutionContext.cs` 的 `ResolveInput`）。每次取值记一条 `InputResolved`；输入名由引擎按属性对象反查自动识别，识别不出（如放在列表或嵌套配置里）记为 `Unresolved`，值照常取得。全仓 38 个节点文件使用 `ResolveInput`，3 处使用 `ResolveDynamicInput`（`VisionPrecisionNodes.cs:223` 的样本列表、`WorkflowVisionCoordinateBinding.cs:24`、`WorkflowSubflowRuntime.cs:17` 的子流程输入映射）。

**核实**　现有节点基本是开头先取输入再操作设备（如 `AxisActionNode.cs:60` 取输入，`:65` 才执行轴动作），且 WFB002 保证绑定来源必然先完成，"执行到一半才发现输入缺失"现实中少见。但这依赖每个节点的写法，没有机制保证。

**结论**（2026-11-18）

- **节点开始工作前，由引擎取齐该节点的所有输入；任何一个取不到，节点直接异常，不进入执行代码。** 不再依赖节点作者"先取输入再动设备"的写法习惯。
- 实施建议：引擎在调用执行代码前，按节点的输入槽元数据（`WorkflowNodeInputLayout`）逐个解析并缓存，同时记录 `InputResolved`；执行代码里的 `ResolveInput(node.Xxx)` 改为直接返回已取好的值。这样 38 个节点的执行代码可以不改。
- 待定细节（实施时确定）：
  - 动态输入（列表元素、子流程输入映射）也需在执行前取齐，需要让引擎能事先枚举这些输入，而不是由执行代码临时拼键名；
  - 是否需要"可选输入"（没取到不算错）。由于 WFB002 已保证绑定来源必然先完成，预计不需要。
- `Unresolved` 只影响记录中的输入名；执行前统一取齐后，输入名由引擎按槽位确定，此问题随之消失。

### R2-d　输入、输出与数据通道梳理　`方向已确认（细节待定）`

**背景**　节点结果不应直接写入流程变量。现有数据通道较多且有重叠，需要整体梳理。以下为 2026-11-19 按代码盘点的现状。

**现有数据通道**

| 通道 | 写入方 | 读取方 | 设计期可检查 |
|---|---|---|---|
| 节点输出（标准输出 + 成员） | 每个节点执行结果；4 个节点为动态输出（`IWorkflowDynamicOutputNode`） | 下游 `WorkflowInput<T>` 绑定（节点 ID + 成员路径） | 是（WFB001～005） |
| 节点输入 `WorkflowInput<T>` | — | 固定值 / 绑定节点输出 / 绑定公共数据（`$global:` 前缀） | 是 |
| 节点输入"三件套" | — | 4 个队列/信号值节点自带 `ValueSource` + `LiteralValue` + `BindingValue`，与 `WorkflowInput<T>` 重复 | 部分 |
| 流程变量：结果副本 | 25 个节点文件的 `ResultVarKey`，执行完把结果再存一份（默认名固定，如 `AxisWaitResult`，不带节点 ID；只有队列初始化、信号批量初始化留空时用 `节点ID.Result`） | 脚本 `GetVariable`、循环块 `ExitVariableName` | 否 |
| 流程变量：恢复内部状态 | 恢复节点写 `DP.WorkFlow.InterruptContext`、`DP.WorkFlow.FaultRequest`、`$CurrentSafePoint`、`DP.WorkFlow.WarningResolution` | 恢复节点、告警协调器 | 否 |
| 流程变量：脚本 | 脚本节点 `SetVariable` | 脚本节点 `GetVariable` | 否 |
| 公共数据 | 只有脚本节点 `PublishData`；宿主 | 绑定 `$global:` | 是（键存在性取决于宿主目录） |
| 信号 | 引发信号节点 | 等待信号节点；子流程继承父信号 | 否 |
| 信号值、队列 | 宿主服务，按字符串键 | 对应节点按键读写 | 否 |
| 子流程接口 | 父侧 `Inputs`（绑定或手动值） → 子流程 `SubflowInputs` | 子流程 `Outputs` 映射（取最新，见 R2-a） | 是 |

**混乱点**

1. 节点结果同时走"节点输出"和"流程变量副本"两条路，后者默认名不唯一、不可检查。
2. 输入有两种表达：`WorkflowInput<T>` 和"三件套"。
3. 恢复机制把引擎内部状态放在用户可见的流程变量里，与用户变量共用一个命名空间。
4. 变量只能按字符串名字读（脚本、循环块退出变量），设计期无法检查拼写或写入顺序。
5. 公共数据只有脚本能写，没有专门的发布方式。
6. 用户眼中的"公共数据"（队列、bool 信号、数值信号、普通数据）在代码里是四套独立机制：`IWorkflowQueueService`、`WorkflowSignalService`、`WorkflowValueSignalService`（宿主服务，节点经 `GetRequiredCapability` 取得，按字符串键访问）和 `IWorkflowPublicDataStore`（通用键值 + 设计期目录 `WorkflowPublicDataCatalog`，仓库中无宿主登记）。设计器只能绑定选择最后一种。

**补充核实**　画布循环节点的计数存在令牌上、按循环节点 ID 区分（`WorkflowEngine.Execution.cs:98`，`token.PrepareLoopIteration(node.Id)`），不在流程变量中，多个循环节点不会混淆。

**结论**（2026-11-19）

数据分为三类，每类只有一种用途：

1. **节点的输入输出**：单个流程内节点之间传递数据。
   - 节点结果只通过节点输出提供，下游用绑定（`WorkflowInput<T>`）获取；
   - **节点结果不再写入流程变量**：去掉 25 个节点的 `ResultVarKey` 结果副本；
   - 输入只保留 `WorkflowInput<T>` 一种写法，队列/信号值节点的"三件套"并入。
2. **流程数据**：单个流程内部私有的数据，**外部不可见**。
   - 引擎自身使用的内部状态（恢复状态、循环块退出判断等）与流程数据明确分开，按节点 ID 区分，不与用户数据共用命名空间；
   - 脚本节点不再直接读写引擎内部状态。
3. **公共数据**：全局数据，所有流程都可以访问。
   - 队列、bool 信号、数值信号、普通数据统一为"公共数据"一个概念，按类型区分，由宿主统一登记和管理；
   - 设计器中都能选择，节点按类型读写；外部可见。

待定细节（后续讨论）：

- 流程数据由谁写、怎么读（专门节点、脚本、绑定选择），以及子流程能否看到父流程的流程数据；
- 循环块退出条件改为什么方式表达（现为填写流程变量名）；
- 公共数据的生存期和范围（进程级 / 设备级 / 可持久化），以及与现有四套服务的迁移方式；
- 画布数据线显示问题（端口固定在右侧、连线固定连到左边中点，`WinForms/.../WorkflowDesignerControl.cs:718`）转 UI 讨论。

#### 公共数据现状盘点（2026-11-19，讨论中）

| 机制 | 值类型 | 操作 | 写入何时生效 | 等待/通知 | 设计期声明 | 范围 |
|---|---|---|---|---|---|---|
| 队列 `IWorkflowQueueService` | `E_SignalValueType` 五种（String/Int32/Int64/Double/Boolean），队列创建时定类型，类型不符抛异常 | 初始化、清空、入队（可去重）、出队、按值移除、读快照、按条件等待；另有一套"兼容字符串"接口 | 立即（节点失败也不回滚） | 有 | 无，各节点手填字符串键和类型 | 取决于宿主注册（`GetRequiredCapability`）；仓库内无宿主注册 |
| bool 信号 `IWorkflowSignalService` | bool | 读、写、取反、等待（可自动复位） | 立即 | 有 | 无 | 同上 |
| 数值信号 `IWorkflowValueSignalService` | 任意对象（节点侧按五种类型解释），服务本身不记类型 | 设置、加、减、等下一次写入 / 已有值或下一次写入并比较；带版本号；另有兼容字符串接口 | 立即 | 有 | 无（有"批量初始化"节点） | 同上 |
| 公共数据仓 `IWorkflowPublicDataStore` | 任意 CLR 对象 | 读、原子写入/删除集合 | 节点成功后才提交 | 无 | 有目录 `WorkflowPublicDataCatalog`（键、类型、显示名、分类），仓库内无宿主登记 | 默认每个根运行一份，父子流程共享；宿主可传入 |
| 流程内一次性信号（`WaitSignals` 节点） | 无值 | 引发、等待全部 | 立即 | 有 | 无 | 单次运行，子流程继承父流程；仓库内没有节点调用"引发" |

兼容性方面的差异：

1. **类型体系不同**：队列和数值信号只支持五种基本类型；公共数据仓支持任意对象（坐标、配方等复杂类型只能放这里）。数值信号服务不记录类型，一处按 Int32 写、另一处按 Double 读需要靠转换。
2. **生效时机不同**：队列、信号写入立即对其他流程可见，节点失败也不撤销；公共数据仓在节点成功后才提交。
3. **能否等待不同**：队列、信号可以等待变化；公共数据仓不能。
4. **声明方式不同**：只有公共数据仓有设计期目录、能在绑定里选择；队列和信号的键分散在各节点配置里手填，同一个键在不同节点里可能被当成不同类型使用。
5. **范围不同**：三个服务的范围取决于宿主注册方式；公共数据仓默认是每个根运行一份。
6. **历史接口**：队列和数值信号各保留一套"兼容字符串"接口。

#### 公共数据结论（2026-11-19）

- **值类型只用 5 种基本类型**（String / Int32 / Int64 / Double / Boolean），以现有队列、bool 信号、数值信号为基础。复杂类型暂不支持，以后确有需要再扩展。
- **三种形态**：
  - bool 信号：读、写、取反、等待；
  - 数值：设置、加减、等待比较，带版本号；
  - 队列：入队、出队、移除、等待，建队时定类型。
- **先登记后使用**：每个公共数据有键、形态、类型、默认值；设计器从登记中选择，不再手填字符串键；设计期检查拼写和类型一致性。
- **可被绑定读取**：节点输入可以绑定数值或 bool 信号的当前值，做类型检查。
- **写入立即生效**（保持现有队列、信号语义），因为其他流程可能在等待。
- **清理**：去掉未使用的公共数据仓 `IWorkflowPublicDataStore` 及其目录，绑定中的"公共数据"改指向新的登记；去掉队列、数值信号的"兼容字符串"接口。
- **新增"流程管理"（流程运行中心）**：由外部程序创建的一个库内对象，不做独立进程或系统服务。负责：
  - **公共数据中心**：所有公共数据的登记和当前值，各流程共用一份；
  - **全局出口**（R1-05）；
  - **流程列表**：加载了哪些流程、各自状态，统一启动和停止。
  
  不使用流程管理时，单个流程自建一个仅供自己使用的公共数据中心，行为与现在一致。
- **流程文件携带公共数据清单**：每个流程文件仍独立保存，并记录自己用到的公共数据（键、形态、类型）。设计器据此选择；加载到流程管理时逐项核对。
- **定义方式：各流程清单的合集，先登记者为准**。中心没有的按清单登记；已有但形态或类型不一致时报错，流程不允许启动。暂不设单独的公共数据定义文件。

待定：

- ~~流程内一次性信号~~ 已定（2026-11-19）：运行内信号（`RaiseWorkflowSignal` / `WaitAllWorkflowSignalsAsync`）只有等待节点 `WaitSignals`、没有任何标准节点或脚本能引发。**去掉运行内信号和 `WaitSignals` 节点，统一使用公共数据中的 bool 信号**（信号设置 + 信号等待；需要时在流程开头复位或使用等待节点的自动复位；等多个信号时串联等待节点，必要时再给等待节点加"等待多个"）；
- ~~公共数据是否需要断电保存~~ 已定（2026-11-19）：每个公共数据可设置是否保持，**默认不保持**，打开后断电保存；后续作为功能包接入 DP.Foundation 时也使用这一设置；
- 流程管理的具体职责（启动顺序、联动停止等）放到第 3 类执行模型中讨论。


### R2-e　资源型输出（图像帧租约）的释放　`已确认`

**现状**　相机节点输出的图像帧是借自相机缓冲的租约，必须归还。

- 同一节点的新输出提交后，旧输出不再可读，引擎立即通过输出投影的 `Retire()` 归还资源（`WorkflowEngine.Execution.cs:306` `RetireOutputs`）；并行作用域完成时同样清理上一圈分支输出。因此循环多少圈，每个相机节点也只占一帧。
- 子流程（Block / LoopBlock）结束时，子运行中尚未归还的资源交给父引擎（`DetachOutputProjections`），子流程成功则挂在父流程中子流程节点的输出上，等该输出被下一次结果替换时一起归还；子流程失败则立即归还（`AdoptChildOutputProjections`）。
- 归还失败计入记录健康状态（`ReportRecordingDegraded`）；归还成功不记事件，符合 R1-01"只记关键事件"。

**问题**　子流程结束时，**所有**未归还的资源都会被父流程保留到下一圈，即使子流程的输出映射根本没有把这张图交出去（只是内部运算用）。每个子流程内的相机节点因此最多同时占两帧。

**结论**（2026-11-19）

- 机制本身正确，保持。
- **子流程结束时按输出配置区分**：只有被子流程输出映射（`Outputs`）引用、需要往外交的资源才交给父流程保留；只在子流程内部使用、没有配置输出的资源，子流程结束时立即归还。
- 归还失败通过 R1-01 的节点提示显示在对应节点上。

## 第 3 类：执行模型

### 更正（2026-11-19 核对代码）

- 候选项中"循环块每圈新建一个引擎"已过时：循环块整个过程只建一个子引擎，每圈再调用一次运行（`WorkflowEngine.Children.cs:16` `OpenChildWorkflowSession`）。
- 原 R3-b"ADR-0006 写子流程复制父变量，代码未复制"不是问题：ADR-0013 已改为子流程拥有独立局部变量，代码与 ADR-0013 一致，ADR-0006 文字未更新。结合 R2-d"流程数据私有"，子流程的流程数据独立。

### R3-a　子流程的运行方式　`已确认（重新评估 ADR-0006）`

**现状**　子流程块（Block、LoopBlock）运行时，父引擎另建一个完整子引擎运行子画布并监管：父引擎用 6 张表跟踪子运行（`WorkflowEngine.cs:24-32`），暂停、挂起、取消逐个转发，子引擎快照逐层上传；每个子运行有独立运行号和记录器。

并行已经是"同一引擎内的作用域 + 分支令牌"实现（`WorkflowEngine.Parallel.cs`），不建子引擎。

**结论**（2026-11-19）

- **子流程改为同一引擎内的"画布作用域"**，照并行作用域的做法：
  - 走到子流程块时开一个画布作用域，令牌带上画布路径（如 `/B`，沿用 `WorkflowRunPreparationPlanner.ChildPath` 的路径写法），子画布节点身份为"路径 + 节点"；
  - 子流程输入放入作用域；子画布只能读本画布内先完成的节点输出和子流程输入，读不到父画布（隔离效果与现在相同），公共数据全局可见；
  - 在同一引擎内走子画布；结束时关闭作用域，按输出映射交出结果，未交出的资源立即归还（R2-e），子画布流程数据随作用域丢弃；
  - 循环块每圈开一次画布作用域，圈数记在令牌的循环计数上，与画布回边循环使用同一套记法。
- **收益**：不再需要父引擎跟踪子引擎的 6 张表、暂停/挂起/取消转发、快照逐层上传、每个子运行一个记录器和运行号；R1-02 父子轨迹只能按时间合并、R1-05"事件额外带所属顶层流程"的问题随之消失。一次运行 = 一个引擎、一份记录、一份快照。
- **需要新做**：节点身份加画布路径（输出存储、记录、快照、节点提示都使用）；读取范围按画布隔离；快照按画布分层供界面钻取。
- **单独试跑子画布**仍可临时建引擎，把子画布当主画布运行。告警处理流程（`WorkflowWarningHandlerCoordinator.cs:61`）和联合恢复（`WorkflowJointRecoveryGroup.cs:102`）不是子流程，继续单独建引擎。
- **对外是接口固定的自定义节点**（现有设计已是如此：`Inputs` 绑定或手动值 → 子画布入口节点；`Outputs` 选来源 → 父画布绑定"子流程块.输出名"）。作用域只改变内部运行方式，不改变对外形态；R2-c"执行前取齐输入"同样适用。
- **接口类型与普通节点输入输出一致**：基本类型、结构化结果（坐标、定位结果、测量结果等，可按成员取）、资源类型（图像帧，按引用传，归还按 R2-e）。手动值只允许基本类型，并与公共数据统一为 5 种（Int32、Int64、Double、String、Boolean；现为 int、double、bool、string 四种）。
- **后续扩展**：子流程保存为可复用的节点类型。届时接口类型必须显式声明，内部来源须与声明一致，否则编译报错。
- **故障恢复**（恢复入口、重跑现按引擎定位，需改为按"路径 + 节点"）改动最大，后续单独讨论。
