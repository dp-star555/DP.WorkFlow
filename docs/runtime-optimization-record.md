# 底层优化项讨论记录

本文记录对 DP.WorkFlow **底层**（编译、执行、数据流转、运行观测）的优化项讨论。目标是先让底层的数据流转正确、可观测，再考虑 UI 怎么展示；UI 层问题暂不在此讨论。

讨论方式：按类别逐类讨论，每一项先记录现状和证据，讨论后再填写结论。**本文只记录，不改代码**；某项确认后，再单独立项实施。

## 讨论规则

每一项包含：

- **现象**：实际发生了什么；
- **证据**：代码位置（`文件:行号`，以 main `d572537` 为准）或可复现的事实；
- **与既有文档的关系**：是否已有设计（`workflow-run-recording-design.md`）、评审条目（`architecture-final-summary.md` 中的 AR-xx）或决策（`decisions/`）；新建议如与已接受的决策冲突，必须明确写出，不能悄悄推翻；
- **方案选项**：列出可选做法及其代价；
- **倾向**：我的建议（可被讨论推翻）；
- **待定问题**：需要你决定的事项；
- **结论**：讨论后填写。

状态取值：`待讨论` / `已确认` / `暂缓` / `否决`。

## 类别与讨论顺序

| 序 | 类别 | 关注点 | 状态 |
|---|---|---|---|
| 1 | 运行事实与记录 | 一次运行中发生了什么、记在哪里、几份记录是否一致 | 讨论中 |
| 2 | 数据流转 | 输出的存取与可见性、输入解析、变量与公共数据等旁路 | 待讨论 |
| 3 | 执行模型 | 子运行、两种循环、并行、多个执行入口 | 待讨论 |
| 4 | 观测接口 | 外部（UI、宿主、分析工具）如何订阅和查询运行信息 | 待讨论 |
| 5 | 正确性保障 | 事件流不变量、回放、测试覆盖 | 待讨论 |
| 6 | 文档模型 | 稳定 ID、过渡投影、模型中的推导状态 | 待讨论 |
| 7 | 节点定义与配置 | 定义分散、版本升级、可变配置与反射快照 | 待讨论 |

先讨论第 1 类，是因为第 2～5 类都要依赖"运行中发生了什么"有一份可靠的记录。

## 第 1 类：运行事实与记录

### 背景：现有设计的原则

`workflow-run-recording-design.md` §5 已确定三层结构：

- **运行工作集**（引擎内部状态）是执行的权威；
- **快照投影**只复制当前可观察状态，大小受"静态节点数 + 当前并行度 + 活动子流程数"限制；
- **运行记录器**分配事件序号、维护内存最近窗口、向宿主配置的 Sink 推送；**记录链路故障必须可诊断，但不能改变执行结果**。

这个原则是对的，本类各项都在它之内讨论。

> 更正：我在前一次总体讨论中提出"以事件流作为唯一事实来源（快照由事件折叠得到）"。对照上述原则，这等于让记录链路成为执行的一部分，与"记录失败不影响执行"冲突，代价也偏大。下面 R1-01 改为在现有原则内的方案，"完全事件溯源"仅作为备选列出。

### R1-01　同一事实写入多处，彼此没有对齐机制　`已确认`

**现象**　同一个状态迁移被分别写进几个互不关联的地方，没有共同的序号把它们对上。快照说"已完成"的节点，轨迹或持久化记录里可能没有对应事件，而任何一方都无法发现这种不一致。

**证据**

- "节点开始"一件事连续写四处：`WorkflowEngine.Execution.cs:107-110`
  - `MarkNodeStarted`：写引擎私有字典 `_nodeRuntime`，快照由此生成；
  - `SafeInvoke(NodeStarted, ...)`：C# 事件；
  - `RecordRunEvent("NodeStarted")`：记录器事件流，轨迹和持久化由此而来；
  - `BeginNodeTiming`：另一套计时。
- `NodeCompleted` 事件里的耗时取自 `_nodeRuntime`（`Execution.cs:197`），而不是由事件时间戳算出，两边各算各的。
- 记录器写入异常被吞掉（`WorkflowEngine.Observation.cs:259`）。按设计这是对的，但设计 §7.4 要求的 `RecordingFailed` 事件没有实现（全仓 0 处），所以丢了记录也看不出来。
- 快照的 `Sequence` 是独立计数（`_snapshotSequence`），与事件 `Sequence` 无关，消费方无法判断"这份快照已经包含到哪条事件为止"。

**影响**　界面、轨迹、持久化记录三方可能各说各话。现场排查时无法判断是"没执行"还是"执行了但没记下来"。

**与既有文档的关系**　符合设计 §5 的分层原则；缺口在于没有对齐手段，以及 `RecordingFailed` 未落地。

**方案选项**

| 选项 | 做法 | 代价 |
|---|---|---|
| A | 维持现状，只补 `RecordingFailed` 计数和事件 | 小；能发现丢记录，但仍无法对齐 |
| B | 每次工作集状态迁移，在同一步里向**内存事件流**追加一条事件（同一把锁、同一序号）；外部 Sink 仍然尽力而为。快照携带"已包含到的最后事件序号" | 中；需要把迁移收敛到少数入口 |
| C | 完全事件溯源：状态由事件折叠得到 | 大；与设计 §5 原则冲突，不建议 |

**倾向**　B。内存事件流属于运行工作集的一部分（可靠、不吞异常），写外部 Sink 的部分仍可失败而不影响执行。这样既保持现有原则，又让"快照—事件"可以对齐、核对。

**待定问题**

1. 内存事件流写入是否允许失败？例如 Payload 编码出错时，是降级为摘要后照常追加，还是丢弃该条？我倾向前者。
2. 快照是否需要增加"最后事件序号"字段？

**结论**（2026-11-18）

- **不引入额外编号做对齐。** 以精确时间戳 + 上下文（哪次运行、哪个节点、哪一次执行）关联还原现场。
- **时间戳改用高精度时钟。** .NET Framework 4.8 下 `DateTime.UtcNow` 默认精度约 1～15ms，快速循环时前后记录可能时间相同。
- **记录原则：只记关键事件，避免过细日志。** 过细的日志会淹没关键信息，反而妨碍排查。
- **记录失败要让人看得到。**
  - 现状：内核已有 `WorkflowRecordingHealth`（已记录、丢失、写失败计数，最后错误及时间）和限频通知 `RecordingHealthChanged`，但宿主和界面都没有使用。
  - 做法：通过下面的"节点提示"展示。
- **新增"节点提示"机制。**
  - 每个节点有一个累计提示列表，存放**不影响引擎运行**的提示。记录丢失是其中一类，以后其他非致命提示也放在这里。
  - 引擎侧产出提示（节点、时间、类别、消息），作为运行状态的一部分供界面读取，不进入执行路径。
  - 界面在节点**右上角外沿**显示黄色角标（与失败的红色区分）；点击查看详情，确认后清除。
  - 超过一定数量后按清理策略处理（具体上限和清理方式待定）。
  - 无法归属到节点的提示（如成批写入文件或数据库失败、运行开始/结束等运行级记录），放在**画布右上角**，使用同一机制。

### R1-02　运行树没有统一的顺序：三套序号，子运行各自计数　`已确认（并入 R1-01）`

**现象**　判断"谁先谁后"没有一个可靠的全局序号。

**证据**

- 一次运行里有三个互不相关的计数器：
  - 节点徽标上的执行序号 `#n`：节点**开始**时递增，引擎字段 `_nodeExecutionSequence`（`WorkflowEngine.Observation.cs:179`）；
  - 输出序号：输出**提交**时递增，`WorkflowRunState._nodeExecutionSequence`（`WorkflowRunState.cs:155`），数据血缘的 `SourceOutputSequence` 用的是它；
  - 事件序号：由记录器分配。
- 每个子运行（子流程、循环块的每一圈）有自己的记录器（`WorkflowEngine.Run.cs:193`、`WorkflowEngine.Continuation.cs:121`），三套序号也都从 1 重新开始。所以在循环块的子画布里，`#n` 每圈都从头编号。
- 合并父子轨迹只能按时间戳排序（`WorkflowEngine.Observation.cs`，`GetTraceBatch` 中的 `OrderBy(Timestamp)`）。
- 本项目同时面向 .NET Framework 4.8（ADR-0022）。在 .NET Framework 上 `DateTime.UtcNow` 的精度通常只有 1～15.6ms，快速循环时父子事件时间戳相同的情况很常见，合并后的先后顺序不确定。

**影响**　
- 你需要的"回环时一眼找到最后执行、导致停机的节点"，在跨子运行时没有可靠依据；
- `#n` 与输出序号不是同一个数，把"第 n 个执行的节点"和"它用了谁的第几次输出"对应起来需要额外换算。

**与既有文档的关系**　设计 §7.2 明确"子 Run 使用自己的 RunId，Sequence 在单个 Run 内单调"，这一点保留不变。这里要补的是"运行树范围的顺序"，与该设计不冲突。

**方案选项**

| 选项 | 做法 | 代价 |
|---|---|---|
| A | 根运行持有一个运行树级的全局计数器，子运行的记录器共享它；每条事件在保留本运行 `Sequence` 的同时，带上全局 `Ordinal` | 小；一个 `Interlocked` 计数 |
| B | 不加全局计数，改为在父运行事件流中记录子运行的开始和结束（带子 `RunId`），靠因果关系排序 | 中；同一时刻父子交错的事件仍无法排序 |
| C | A + B | — |

**倾向**　C。全局 `Ordinal` 解决排序；子运行开始和结束事件解决"这一圈属于父节点的哪一次执行"。另外建议明确：
- UI 上的 `#n` 是用开始序号，还是改用全局 `Ordinal`；
- 输出序号与开始序号是否合并成一套。

**待定问题**

1. `#n` 的语义：按"本画布内执行开始的顺序"（现状），还是按"整个运行树的全局顺序"？在循环块子画布里，你希望看到每圈重新编号，还是全局连续编号？
2. 是否接受合并"开始序号"和"输出序号"？合并后，一次执行有唯一编号，输出直接引用这个编号。

**结论**（2026-11-18）　不引入全局编号。先后顺序靠高精度时间戳 + 上下文关联，见 R1-01。

遗留问题：循环块子画布里 `#n` 每圈重新编号，这一点转到第 3 类讨论两种循环的语义时一并确定。

### R1-03　事件缺口　`方向已确认（细节待定）`

**现象**　有些事件设计里要求了但没有实现；有些实现得比设计少；还有一些执行语义没有对应的事件。

**证据**（全仓检索事件键）

| 情况 | 事件 | 说明 |
|---|---|---|
| 设计要求，未实现 | `RunInterruptedDetected`、`RecordingFailed` | 0 处 |
| 实现少于设计 | `VariableChangesCommitted`、`PublicDataChangesCommitted` | 设计 §7.4 要求"Key 和值摘要"，实现只记了 Key（`Execution.cs:366`） |
| 未设计，缺失 | 并行开始（只有 `ParallelMerged`）、令牌分叉和结束 | 并行分支何时分开、谁和谁汇合，只存在于快照字典里 |
| 未设计，缺失 | 循环一圈确认 | 第几圈只能从执行身份里的 `LoopIteration` 推断 |
| 未设计，缺失 | 子运行开始和结束（在父运行事件流中） | 父子关系只能通过子运行事件里的 `ParentRunId` 反查 |
| 未设计，缺失 | 暂停、恢复、外部 Hold 增删、信号触发和等待 | 停机或等待的原因不在记录里 |
| 未设计，缺失 | 实际走的连线 | 见下 |

关于"实际走的连线"：`NodeCompleted` 已记录所选出口，配合执行计划本可以推出下一节点。但 `RunStarted` 没有记录流程的身份或版本（`WorkflowEngine.Run.cs:203`），离线拿到记录时不知道对应的是哪一版流程，也就推不出路径。

**影响**　事后复盘时，无法完整回答"为什么停在这里""当时在等什么""走了哪条分支"。

**方案选项**

- 按上表逐个补齐。
- 对"实际走的连线"有两种做法：
  - 每次跳转记一条事件（量较大）；
  - 只在 `RunStarted` 里记录流程身份（文档内容哈希或版本号），由离线工具结合执行计划推导路径。

**倾向**　
- 补齐表中"设计要求未实现"和"实现少于设计"两类；
- 新增并行开始、子运行开始和结束、暂停/恢复/Hold、信号这几类；
- 连线选择"`RunStarted` 记录流程身份 + 离线推导"，默认不逐跳记录；
- 循环一圈确认，等第 3 类统一两种循环的语义后再定。

**待定问题**

1. 变量和公共数据的"值摘要"是否有敏感数据或体积方面的顾虑？例如配方参数、图像引用。
2. 流程身份用文档内容哈希，还是由保存时递增的版本号？

**结论**（2026-11-18）

- 暂停、恢复、外部挂起（Hold）的增加和解除，以及节点开始等待信号或条件、等到或超时，**需要记录到流程记录中**。现状是这些都不记录（`WorkflowEngine.Control.cs` 中没有任何写记录的调用），停机后无法判断原因。
- 每类事件只在发生时记一条，平时不产生额外日志。
- 具体事件清单和字段（以及表中其他缺口），等第 2、3、6 类把数据流转、执行模型和文档模型的结构梳理清楚后再定。

### R1-04　观察者在执行线程上同步执行　`待讨论`

**现象**　UI 等订阅方的处理逻辑直接在节点执行线程上同步运行。订阅方处理得越慢，流程跑得越慢。订阅方抛出的异常被吞掉，宿主无从得知。

**证据**

- `SafeInvoke(NodeStarted, node)` 在执行线程上同步调用（`Execution.cs:108`）；`NodeCompleted`、`NodeTrace`、`StateChanged` 同理。
- 有订阅者时，快照在执行线程上、在调度锁 `_stateSync` 内构造（AR-17）；子运行的快照还会逐层传给父引擎再发布一次。
- AR-17 阶段 1 只解决了"无订阅者不构造"。"每次迁移发布一次"已被测试 `SlowSnapshotObserver_IsExcludedFromSingleNodeExecutionTime` 写成契约。
- AR-19（观察者异常无诊断出口）仍未关闭。
- 上次"快速循环时界面卡死"的修复做在 UI 一侧（运行绑定节流、监视页合并刷新），引擎侧"同步通知"的结构没有变。

**影响**　生产节拍受 UI 订阅方影响；订阅方的故障不可见。

**与既有文档的关系**　ADR-0003 规定"事件观察者异常不得改变流程结果"，这一点保持。AR-17 指出：合并发布会改变一条已被测试固定的契约，必须显式设计，不能顺手改掉。

**方案选项**

| 选项 | 做法 | 代价 |
|---|---|---|
| A | 维持同步通知，只补 AR-19 的异常计数和诊断 | 小；节拍问题仍在 |
| B | 执行线程只更新工作集和内存事件流（R1-01 B），然后发出一个很轻的"有新序号"通知；订阅方在自己的线程上按需取快照或增量事件 | 中；需要改写 AR-17 那条测试契约，并说明新契约 |
| C | 独立分发线程 + 有界队列，队列满时按明确策略合并 | 中；多一个线程，要定义满队列策略 |

**倾向**　B（并补上 AR-19）。新契约可以写成："每次迁移都会产生一条事件，不会丢；快照按需构造，不再保证每次迁移都发布一次。"

**待定问题**

1. 有没有宿主（不是 UI）依赖"每次迁移同步回调"来做逻辑？例如设备联锁、MES 上报。如果有，它应当改为订阅事件流，而不是快照回调。

**结论**　（待讨论）

### R1-05　没有默认持久化，现场事后复盘依赖宿主自行实现　`待讨论`

**现象**　运行事件只保存在内存窗口里：每个运行最近 2000 条（`WorkflowExecutionOptions.MaxTraceEntries`），每个复合节点的子运行历史也最多 2000 条。程序关闭或窗口滚动后，记录就没了。

**证据**

- 仓库里只有 `IWorkflowRunEventSink` 接口和记录器，没有任何 Sink 实现（文件、SQLite 等均无）。
- 设计 §5 写明 Sink "可不配置（仅保留内存最近窗口）"，由宿主选择。

**影响**　"夜里停机、早上查原因"这类场景，如果宿主没有自己实现 Sink，就没有可查的记录。

**方案选项**

- A：维持现状，由宿主实现。
- B：在仓库里提供一个默认的本地滚动文件 Sink（例如按运行或按天分文件、JSON Lines 格式、带容量上限），宿主可以选择启用。
- C：B 加一个离线查看工具（读取文件、按序号回放、筛选），与第 4 类观测接口共用查询逻辑。

**倾向**　B，C 放到第 4、5 类讨论时再定。

**待定问题**

1. 现场是否允许写本地磁盘？保留多久、上限多大？
2. 是否已有 MES 或数据库方面的上报要求？如果有，默认 Sink 的格式最好与之兼容。

**结论**　（待讨论）

## 第 2～7 类：候选项（讨论到时再展开）

以下只列已发现的问题和证据入口，讨论到该类时再按上面的格式补全。

### 第 2 类：数据流转

- **R2-a** 存在两种读取语义：
  - 按令牌和作用域的可见性读取（ADR-0005，正确）；
  - 无视令牌、直接取"最新值"：`WorkflowBindingResolver.ResolveLatest`（`Data/WorkflowBindingResolver.cs:117`）和 `_latestNodeOutputs`。
  
  子流程对外输出用的是后者（`Nodes.Composite/WorkflowSubflowRuntime.cs:38`），子流程内部有并行分支时可能取到任意一个分支的值。
- **R2-b** 每次按可见性读取，都会把整个输出历史复制一遍再倒序查找（`WorkflowRunState.cs:181`）。
- **R2-c** 输入在 Handler 执行过程中按需解析，输入槽靠自动识别，识别不出时记为 `Unresolved`。设计 §8.3 是有意这样选的（不要求 Handler 手写键名），需要权衡"执行前统一解析"的好处与按需解析的灵活性。
- **R2-d** 变量、公共数据、信号、队列是图外的旁路：编译期绑定分析看不到，节点包里已有 34 个文件读写变量。
- **R2-e** 资源型输出（图像租约等）依赖"新输出覆盖旧输出时释放"（`WorkflowRunState` 类注释），释放没有记录。

### 第 3 类：执行模型

- **R3-a** 子运行是独立引擎，父引擎负责监管（ADR-0006，已接受）：
  - 循环块每圈新建一个引擎（`Execution/WorkflowEngine.Children.cs:27`、`:217`）；
  - 父引擎用 6 个字典跟踪子运行；
  - 暂停和 Hold 靠逐个转发（`Children.cs:40-49`）。
  
  是否改为"同一调度器内的嵌套作用域"，属于**重新评估 ADR-0006**，需要单独讨论。
- **R3-b** ADR-0006 写的是"子流程使用复制父变量的上下文"，但 `WorkflowContext.CreateChildScope`（`State/WorkflowContext.cs:145`）只共享公共数据和信号，没有看到复制变量。需要核实是实现偏离了 ADR，还是变量在别处传入。
- **R3-c** 两种循环语义不同：
  - 画布回边 Loop：令牌上的迭代计数；
  - LoopBlock：每圈一个新的子运行。
  
  "第几圈"在两种循环里含义不一致。
- **R3-d** 创建引擎的入口有 5 处：
  - 宿主；
  - 子运行 2 处；
  - 联合恢复；
  - `Nodes.Process` 里的告警处理。

### 第 4 类：观测接口

- **R4-a** 观测现在有三条路，各有各的线程语义：
  - 五个 C# 事件；
  - 主动拉取快照；
  - 主动拉取轨迹（#68 已改为按游标增量读取）。
- **R4-b** 运行状态推到界面没有统一节拍：运行绑定节流 50ms、画布定时器 100ms、监视页 250ms，各管各的。

### 第 5 类：正确性保障

- **R5-a** 事件流上没有不变量检查，例如：
  - 每个开始事件都有且只有一个结束事件；
  - 每个 `InputResolved` 指向的输出都已提交且未失效；
  - 令牌的分叉与汇合配平。
- **R5-b** 持久化只有 9 个测试，迁移逻辑覆盖偏薄。
- **R5-c** 没有回放测试：同样的输入是否产生同样的事件序列。

### 第 6 类：文档模型

- **R6-a** 连线没有稳定 ID，布局按下标对应连线（`WorkflowConnectionLayout.ConnectionIndex`，`Core/Documents/WorkflowDocument.cs:153`）。
- **R6-b** `CanvasProjection` 仍在 13 处使用，包括 Core、持久化和 `Nodes.Process`（ADR-0011 定位为过渡投影）。
- **R6-c** 连线模型混入了推导状态 `State`、`Diagnostic`（`Core/Documents/WorkflowConnectionModel.cs:53-56`）；内核里写着 UI 默认尺寸（`WorkflowCanvasModel.cs:42`）。

### 第 7 类：节点定义与配置

- **R7-a** 一个节点的定义分散在多处：
  - 模型特性；
  - 端口写在注册调用里（`Nodes.Standard/WorkflowStandardNodes.cs:62`）；
  - Handler 在另一处注册（同文件 `:137`）；
  - 图标在 UI 映射表里。
- **R7-b** 节点版本不一致时直接抛异常，没有升级钩子（`Persistence.Json/WorkflowDocumentJsonStore.cs:288-291`）。
- **R7-c** 配置隔离依赖反射深拷贝（`Core/Compilation/WorkflowNodeConfigurationSnapshotter.cs`，即 AR-03）。
